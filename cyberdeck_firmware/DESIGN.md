## 0. 確定事項

ABOUT.md の「決めてほしいこと」と、2026-08-27 のヒアリングで確定した内容。

| 項目 | 決定 |
|---|---|
| 言語 / SDK | C11 + ESP-IDF v5.5.5 (`C:\DATA-0\Espressif\esp-idf-v5.5.5`) |
| ターゲット | `esp32s3` |
| 試作機 | M5Stack CoreS3 (COM22 に接続確認済み。ESP32-S3 rev v0.1 / 16MB flash / USB-Serial-JTAG) |
| 最終ハード液晶 | 480x320 SPI |
| 端末セル | 半角 6x12 / 全角 12x12 → **80桁 x 26行** |
| フォント | 東雲フォント 12px (BDF, Public Domain) |
| 試作機の入力 | PC からシリアル経由でキーイベントを注入 |
| 開発優先順位 | M0 基盤 → **M1 VT+コンソール → M2 WiFi+SSH** → M3 シェル/周辺 → M4 SD → M5 SKK → M6 エディタ → M7 最終ハード → M8 wasm |
| ワープロ | microSD 上のプレーンテキストを編集する簡易エディタ (SKK 併用) |
| GUI ライブラリ | 使わない。テキストグリッドを自前描画（LVGL は依存とサイズが見合わない） |

### 画面レイアウト (480x320)

```
480 / 6  = 80 桁
320 / 12 = 26 行 = 312px、余り 8px を最下段のステータス帯に使う

+---------------------------------------------------+ y=0
| テキストグリッド 80 x 26 (6x12 セル)              |
|                                                   |
+---------------------------------------------------+ y=312
| ステータス帯 8px: WiFi / SKKモード / SD / 電池    |
+---------------------------------------------------+ y=320
```

試作機 CoreS3 は 320x240 なので同じフォントで **53桁 x 20行**。
桁数はコンパイル時定数ではなく実行時にパネル寸法から算出する（両方で同じバイナリ設計が動くこと）。

## 1. 最重要の設計方針: ホスト検証可能なコア

ABOUT.md 「パソコン上で検証できるところは積極的にパソコン上で検証する」を
アーキテクチャ要件として扱う。

**ESP-IDF のヘッダを一切 include しない純 C のコア**と、**薄いポート層**に分ける。

ホスト側でユニットテストするもの（＝ `esp_*` / `driver/` に依存してはいけない）:

- VT/ANSI エスケープパーサと画面バッファ
- UTF-8 デコーダ + East Asian Width（全角判定）
- グリフラスタライザ（テキストグリッド → RGB565 キャンバス）
- SKK 変換エンジン（ローマ字かな変換、辞書検索、送り仮名処理）
- 行編集・ヒストリ、シェルのコマンドラインパーサ

ポート層に押し込むもの:

- `esp_lcd` / SPI、WiFi、SDMMC/SDSPI、GPIO/I2C/ADC/UART、FreeRTOS、NVS、USB

この境界を最初のコミットで作る。VT パーサに `ESP_LOGI` が生えてから分離するのは書き直しになる。

## 3. 開発ループ（AI エージェントが自律的に回せること）

ABOUT.md の「AIエージェントが自律的にコーディング、実行、デバッグできるように」への回答。

### 3.1 ログは必ず有限時間で取れること

`idf.py monitor` は終了しないのでエージェントからは使えない。
`tools/cdk.py` に**タイムアウトとセンチネル付き**のシリアルリーダを実装する。

```
python tools/cdk.py flash             # ビルド + 書き込み + リセット
python tools/cdk.py log --timeout 10  # 10秒 or センチネルまで読んで終了
python tools/cdk.py boot              # リセットして起動ログを取り、READY 到達で終了
```

ファーム側は起動完了時に `#CDK-READY` を出す。これがセンチネル。

### 3.2 キー入力の注入

```
python tools/cdk.py type "ls -la\n"
python tools/cdk.py key ctrl+c
python tools/cdk.py key f1
```

ファーム側では「シリアルから来たキーイベント」と「USB キーボードから来たキーイベント」を
`cdk_key_event_t` に正規化して同じ経路に流す。試作機で書いたテストが実機でもそのまま通る。

### 3.3 スクリーンショット

**パネルから読み戻さない。** SPI 液晶コントローラのリードバックは信頼できないか、そもそも無い。
代わりに PSRAM 上のキャンバスを唯一の真実とし、描画は必ずキャンバス経由で行い、
コマンドでその内容をダンプする。

```
python tools/cdk.py shot out.png      # RAW 取得 → ホストで PNG 化
```

副作用として、ホスト側のユニットテストでも同じキャンバスをレンダリングして
PNG を diff できる（実機なしで表示の回帰テストができる）。

### 3.4 チャネル構成

**既定は 2 チャネル**にする。

| チャネル | 物理 | 用途 |
|---|---|---|
| CTRL | USB-Serial-JTAG (**COM22**) | `cdk_proto` バイナリフレーム専用。ログを一切流さない |
| LOG | UART1 → CoreS3 PORT.C (G17=TX / G18=RX) → FT232 (**COM75**) | `ESP_LOG` のテキスト出力専用 |

FT232 は 2026-08-27 に接続確認済み（`FTDIBUS\VID_0403+PID_6001`）。

**最終ハード (v1) では 3 つの役割の乗り方が変わる。** USB を OTG ホストに
使うので USB-Serial-JTAG が無く（HARDWARE_DESIGN.md F-1）、
制御チャネルは UART1 に移る。

| 役割 | 中身 | CoreS3 | v1 |
|---|---|---|---|
| PROG | 書き込み。**EN と GPIO0 を叩ける線** | USB-Serial-JTAG | UART0 の USB シリアル |
| CTRL | `cdk_proto` のフレーム | 同上 | **UART1 (G16/G15) 921600** |
| LOG | `ESP_LOG` | FT232 → UART1 | UART0（PROG と同じ） |

**リセットの掛け方も違う**（USB-Serial-JTAG と普通の USB シリアルで
DTR/RTS の使い方が別）。取り違えると症状が「起動ログが出ない」だけになり、
ポートの問題だと気づきにくい。`cdk.py` は `.cdk_board` を見て
自動で使い分ける（`BOARD_PORTS`）。

制御チャネルを 921600 にしたのは、スクリーンショットが 480x320 で 300KB
あるため。ログと同じ 115200 だと 1 枚 26 秒かかる。

理由: 1 本に多重化すると、ROM ブートローダのチャタリング、パニック時のバックトレース、
`ESP_LOG` に混じるバイナリなど**こちらが制御できない出力**がフレームの中に割り込む。
デバッグチャネル自体が信用できなくなると、以降の全マイルストーンが遅くなる。
配線 3 本（TX/RX/GND）で問題のクラスごと消せるので、そちらを取る。

CH340 を繋げない状況のために **1 チャネル縮退モード**も持つ（`CDK_LINK_SINGLE`）。
そのときは CTRL と LOG が COM22 に同居する。フレーム形式は縮退モード前提で設計しておく:

```
magic(4) = 0x1B 'C' 'D' 'K'   ESC で始めるのでテキスト行として解釈されない
type(1) len(4,le) payload(len) crc32(4,le)
```

ホスト側リーダは**再同期する**こと。すなわち magic を見つけてもフレームを信用せず、
CRC が合わなければ 1 バイト捨てて magic を探し直す。長さフィールドを盲信して
その分読み飛ばす実装にしない（同期外れが一度起きたら復帰できなくなる）。

実装は `components/cdk_proto/`（ホストとデバイスで同一ソースを共有）。

M0 で踏んだ罠: **`usb_serial_jtag_write_bytes()` は TX リングバッファより
大きい書き込みができない。** 内部で丸ごとリングに積むので、リングを超える要求は
何度呼んでも 0 を返し続ける。`port_link` では 512 バイトずつに分割して渡している。

## 4. 表示

### 4.1 パネル

CoreS3 の LCD (ILI9342C) はバックライトと周辺電源が **AXP2101 PMIC と AW9523 I/O エキスパンダ経由**で
ゲートされている。この初期化順序を外すと画面は真っ黒のまま無言で失敗する。
ピンマップと電源投入シーケンスは自前で書かず、公式 BSP から取る。

```
idf.py add-dependency "espressif/m5stack_core_s3^2.0.0"
```

最終ハードは BSP を持たないので、`port_display` は
`bsp_*` を直接呼ばず `cdk_display_init()` / `cdk_display_flush()` の裏に隠す。

M0 で実測した BSP の性質:

- `bsp_display_new()` が AXP2101 / AW9523 の電源投入、SPI3 初期化、
  ILI9342C の reset/init/invert までやってくれる。LVGL は不要。
- ただし `esp_lcd_panel_disp_on_off(panel, true)`、`bsp_display_brightness_init()`、
  `bsp_display_backlight_on()` は自分で呼ぶ必要がある。
- 回転・反転は不要（`swap_xy` / `mirror_x` / `mirror_y` すべて false）。
- **`BSP_LCD_BIGENDIAN = 1`**。パネルはビッグエンディアンの RGB565 を期待する。
  キャンバスはネイティブ（リトルエンディアン）なので転送時に `__builtin_bswap16` する。
- **PSRAM は quad**。`CONFIG_SPIRAM_MODE_OCT=y` にすると
  `PSRAM chip is not connected, or wrong PSRAM line mode` で起動時に abort する。
- 起動時の `i2c.master: Please check pull-up resistances` は CoreS3 では正常。

### 4.2 キャンバスと転送

- キャンバス: `RGB565`、PSRAM 上。480x320 で 300KB、320x240 で 150KB。
- 描画はすべてキャンバスに対して行う。
- **行単位のダーティ**を持ち、変更のあった行帯だけ `esp_lcd_panel_draw_bitmap` で転送する。
  端末は全画面書き換えが少ないので、これで SPI 帯域はまず問題にならない。

> 注意: キャンバスのダーティは**行ごとのビットではなく min/max の 1 本の帯**。
> カーソルが 1 行目から最終行へ飛ぶと、間の行が無傷でも全画面を転送する。
> 320x240 で 150KB、40MHz SPI で約 30ms + バイトスワップ。
> M1 では問題にならないが、SSH で対話していると効いてくる。
> 実際に体感したら行ごと、あるいは連続する行の塊ごとの管理に変えること。
> それまでは前倒しで最適化しない。
- 転送は DMA。**バウンスバッファを 2 枚用意して交互に使う**。
  `esp_lcd_panel_draw_bitmap` の色データは非同期だが、次の呼び出しが
  CASET/RASET コマンドを送る前に in-flight の転送を必ず回収する
  （`esp_lcd_panel_io_spi` の実装）。したがって交互に使えば、
  これから書き込もうとしているバッファの転送は必ず完了している。
  `on_color_trans_done` の登録は不要（BSP が作った io には登録できない）。
- ILI9342C はビッグエンディアンの RGB565 を期待するので、
  バウンスバッファへ写すときに `__builtin_bswap16` する。

### 4.3 テキストグリッド → ピクセル

セルは (文字コード, 前景色, 背景色, 属性) を持つ。属性は bold / reverse / underline / 全角右半分。
再描画はダーティセルのみ 6x12 (or 12x12) を書き込む。

## 5. フォント

### 5.1 東雲 12px

- ライセンス: **Public Domain**
- 入手: `http://openlab.ring.gr.jp/efont/dist/shinonome/shinonome-0.9.11p1.tar.bz2`
  （**https は繋がらない**。http で取ること）
- 使うファイル:

| ファイル | 収録 | 寸法 | 割り当て |
|---|---|---|---|
| `shnm6x12a.bdf` | ISO 8859-1 | 6x12 | U+0020..U+00FF |
| `shnm6x12r.bdf` | JIS X 0201 | 6x12 | U+FF61..U+FF9F（半角カナ） |
| `shnmk12.bdf` | JIS X 0208 | 12x12 | euc_jp 経由で Unicode へ |

`tools/mkfont.py` が BDF を読んでバイナリブロブ
`components/cdk_font/shinonome12.cdkfont` を作る。
**ブロブはリポジトリにコミットする**（BDF アーカイブは 4.6MB あるので入れない）。
ブロブは `EMBED_FILES` でフラッシュに焼き込む。SD もファイルシステムも要らない。

```
python tools/mkfont.py <shinonome-0.9.11/bdf> -o components/cdk_font/shinonome12.cdkfont
```

実測 (2026-08-27):

| データ | サイズ |
|---|---|
| グリフ 7,269 字（漢字 6,868 / 罫線 128 / ブロック 32 / 記号 43） | — |
| 索引 (u16 コードポイント + u32 エントリ) | 42.6 KB |
| ビットマップ | 164 KB |
| **合計** | **207 KB** |

ブロブ形式は `tools/mkfont.py` の docstring が正。
`cdk_font_open()` が全セクションの範囲を検証してから開く。

### 5.2 自前で描いたグリフ

東雲に無い、または全角しか無くて使えないものを `mkfont.py` が生成する。

- **罫線素片 U+2500..U+257F（128 字）**
  JIS X 0208 にも入っているが**全角**。端末は East Asian Width = Ambiguous に従って
  **半角**として数えるので、全角グリフを当てると必ず桁がずれる。
  上下左右の腕の太さ（無し / 細 / 太 / 二重）から 6x12 で組み立てる。
  腕はセルの端まで届かせて、隣のセルと線が繋がるようにする。
  破線は実線、角丸は普通の角で近似。
- **ブロック要素 U+2580..U+259F（32 字）** — 塗り分けなので手続き的に生成。
- **記号 43 字** — `SYMBOLS_SRC` に 6x12 の点図として直接書いてある。
  `─ – — … • ← ↑ → ↓ ⇒ ≠ ≤ ≥ ■ □ ▲ ▼ ◆ ○ ● ★ ✓ ✗ π` など、
  CLI が実際に使うもの。DEC 特殊グラフィクス (`ESC ( 0`) の写像先も全部ここで埋めている。
- **notdef（げた）** — 半角/全角それぞれ。斜線ではなく枠にして空白と区別する。

### 5.3 幅とグリフの不一致を許さない

`cdk_font_glyph(font, cp, cells, &g)` は、見つかったグリフの幅が要求セル数と
違えば **notdef を返す**。グリフがあっても使わせない。
桁がずれるくらいなら げた を出す方がましだから。

この規則の帰結として、Ambiguous 幅でグリフが全角しか無い文字
（ギリシャ文字、キリル文字、丸数字など）は げた になる。
CLI 用途では実害が小さいと判断して M1 では放置する。
将来 `set ambiwidth double` を入れるなら、`cdk_char_width` と
グリフ選択の両方を同時に切り替えること。

### 5.4 まだ出せないもの

- **Powerline / Nerd Font 記号 (U+E0A0〜, U+F000〜)**: 非対応。
  → SSH 先のプロンプト設定でこれらを使わないようにしてもらう。
- **絵文字**: 非対応。げたで表示し、幅だけは全角 2 セルとして正しく数える。
- **ハングル・キリル拡張など**: グリフ無し。幅は正しい。

「表示できないこと」より「桁がずれること」の方が端末としては致命的なので、
**幅計算は必ず Unicode East Asian Width に従い、グリフの有無と切り離す**。

## 6. ターミナルエミュレータ

### 6.1 パーサ

Paul Williams の DEC ANSI 状態機械をそのまま実装する（GROUND / ESCAPE / CSI_* / OSC_* / DCS_*）。
未知のシーケンスは黙って捨てる（画面を壊さないことが最優先）。

### 6.2 対応する制御

ABOUT.md のリストをそのまま実装可能な粒度に展開したもの。

| 分類 | シーケンス |
|---|---|
| C0 | `BEL LF CR BS HT`（`VT` `FF` は LF 扱い） |
| カーソル移動 | `CUU CUD CUF CUB` (`CSI A/B/C/D`), `CNL CPL` (`E/F`), `CHA` (`G`), `CUP` (`H` / `f`), `VPA` (`d`) |
| 画面消去 | `ED` (`CSI J`) 0/1/2/3 |
| 行消去 | `EL` (`CSI K`) 0/1/2 |
| 文字操作 | `ICH IL DL DCH ECH` (`@ L M P X`) — CLI の行再描画で必須 |
| SGR | 0,1,2,4,7,22,24,27, 30-37, 40-47, 90-97, 100-107, `38;5;n` / `48;5;n`（256色）, `38;2;r;g;b`（truecolor → RGB565 に丸め） |
| カーソル保存/復元 | `DECSC` / `DECRC` (`ESC 7` / `ESC 8`), `SCOSC` / `SCORC` (`CSI s` / `CSI u`) |
| スクロール | `DECSTBM` (`CSI r`), `SU` / `SD` (`CSI S` / `CSI T`), `RI` (`ESC M`) |
| スクロールバック | 200 行。`Shift+PgUp` / `PgDn` で遡る。`CSI 3J` で消す（§6.5） |
| モード | `DECTCEM`(25: カーソル表示), `1049` / `47`（代替画面）, `2004`（bracketed paste）, `1000` / `1002` / `1006`（マウス。**受理して無視**） |
| 問い合わせ | `DA` (`CSI c` → `ESC[?6c`), `DSR` (`CSI 6n` → カーソル位置) |
| OSC | `0` / `2`（タイトル → ステータス帯に出す）。それ以外は読み捨て |
| 文字集合 | `ESC ( B` のみ受理。DEC 特殊グラフィクス `ESC ( 0` は罫線にマップ |

**省略するもの**: DCS / Sixel、ReGIS、ソフトフォント (DECDLD)、二重幅行 (DECDWL)、
プリンタ制御、Shift_JIS の直接受理。CLI 用途で必要にならない。

### 6.3 端末種別

`TERM=xterm-256color` を名乗る。`CSI c` (DA) には `ESC[?62;22c`（VT220 相当）を返す。
上記に無いシーケンスが来ても壊れないことを、ホスト側テストで確認する
（`t->stat_unknown` に捨てた数が溜まるので、実機でも異常を検知できる）。

**太字の扱い**: SGR 1 は字を太らせず、前景色を明るい方（パレット 0-7 → 8-15）に振る。
6px 幅で字を太らせても潰れて読めないため。xterm の既定と同じ振る舞い。

### 6.4 ホスト側テスト

```
host/fixtures/vt/NNN_name.in    # 入力バイト列
host/fixtures/vt/NNN_name.txt   # 期待するグリッド（テキスト + 属性）
```

`vttest` の出力や実際の `claude` / `codex` CLI のログを流し込んで回帰させる。

同じフィクスチャを実機の検証にも使う（M1 で実装済み）。

いるので、実機とホストが文字通り同じバイト列を食べている。
これで「実機だけで壊れている」ことを機械的に切り分けられる。

### 6.5 スクロールバック (2026-08-31)

画面からあふれた出力を `Shift+PgUp` / `Shift+PgDn` で遡れる。**200 行**。

それまでは「画面 = 全部」で、`cdk__scroll_up` が上の行を `memmove` で
上書きして捨てていた。`ls -l` や `make` の出力、`wasm run` のログ、
SSH 先の `dmesg` — この機械でいちばん普通にやることが、あふれた瞬間に
読めなくなっていた。§12 の #2「26 行しか無い」を、行数を増やさずに
和らげる方向の答えでもある。

#### 積むのは「画面から永久に消える」経路だけ

`cdk__scroll_up` の中では積まない。あの関数は 3 経路から呼ばれる:

| 経路 | 積むか |
|---|---|
| `cdk__index`（LF / 遅延折返し）が最下行で | **積む** |
| `CSI S` (SU) | **積む** |
| `cdk__delete_lines` (DL, `CSI M`) | **積まない** |

DL は `t->top` を一時的に `t->cy` に**すり替えて**呼ぶ。中で積むと
`vi` や `less` の行削除が履歴に流れ込む。積むのは上の 2 か所から
明示的に `cdk__hist_push(t, n)` を呼ぶ形にして、**grep で「積む場所」が
2 か所に見える**ようにした。

条件は 3 つとも要る:

```c
!t->alt_active && t->top == 0 && t->bot == t->rows - 1
```

`top == 0` だけでは足りない。`ESC[1;20r` のように**上端はそのままで下だけ
狭めた**領域だと `top == 0` は真になるが、row 0 から出ていく行は画面から
消えていない（下の行はそのまま残る）。部分領域のスクロールを履歴に
入れないのは xterm と同じ。

#### 描画の継ぎ目は 1 か所だった

`cdk_screen_draw` は行を **`cdk_term_row(t, y)` だけ**から読む。そこに
表示オフセットを入れたので、描画側の変更は 3 点で済んだ:

- 遡っている間は**全行描く**。ダーティは画面行に対する印で、遡っていると
  表示行とずれる。**判定は `cdk_screen_draw` の中で行う**（呼び出し側に
  `all=true` を書いて回ると、直し忘れた経路だけ古い絵が残る）
- カーソルを描かない（見ている行は入力位置と関係がない）
- 未確定文字列を重ねない（`t->cy` を見ているので位置が嘘になる）

表示行 `y` の対応（`k = view_off`）:

```
y <  k : 履歴の (hist_len - k + y) 行目
y >= k : 画面の (y - k) 行目
```

**`cdk_term_init` の形は変えていない。** 履歴は後から
`cdk_term_set_history` で足す口にした。呼ばなければ今までとまったく同じ
挙動なので、`cdk_render`（ホストの基準レンダラ）はそのままで、
`shot --verify` の比較が動かない。

#### `view_off` を 0 に戻す場所

取りこぼすと `cdk_term_row` が環の最も古い行より前を指して**黙ってゴミを
読む**。そのうえで `cdk_term_row` 側でも `hist_len` で頭打ちにしてある。

| いつ | |
|---|---|
| `cdk_term_reset`（RIS） | 履歴も消す |
| `cdk_term_hist_clear`（`CSI 3J`） | 遡っている最中に来る |
| `cdk_term_set_history`（2 回目・行数変更） | 環の巻き方が変わるので中身ごと捨てる |
| 代替画面へ入る | `cdk__switch_screen` の中。**`alt_active` が変わる唯一の場所** |

`CSI 3J` は履歴を持つまで `2J` と同じ扱いだった。いまは本来の意味
（画面 + スクロールバックを消す）になっている。

#### 入力の割り込み位置は動かせない

`route_key` の「再接続の中止」の直後・SKK より前。

- **これより下（SKK の下）は駄目。** `cdk_skk_key` は `▽` 変換中、
  文字にならないキーを外へ漏らさない。変換中だけ効かなくなる。
- **さらに下も駄目。** `SESSION_EDIT` / `WASM` / `SSH` の分岐はどれも
  無条件に return するので、シェル以外では一生届かない。
- **これより上も駄目。** 「どのキーでも再接続を中止する」は意図して
  置かれた契約。そのぶん**再接続を待っている間はスクロールが効かない**
  という割り切りを取った。

動けなかったときはキーを消費しない。代替画面では履歴が無効なので、
`Shift+PgUp` はそのまま下へ落ちてエディタの PgUp になる。

遡っている最中に**それ以外のキーを打つと最下部へ戻す**（キーは消費しない）。
遡ったまま入力すると、打った字が見えないところへ出ていって混乱する。

#### メモリ

1 行 = 桁数 x 16 バイト（`cdk_cell_t` が 16 バイト）。

| | 1 行 | 200 行 |
|---|---|---|
| 80 桁（等倍） | 1,280 B | 256 KB |
| 40 桁（2 倍表示） | 640 B | **128 KB**（実測値） |

起動時に PSRAM から 1 回だけ確保する。**内部 DRAM には置かない**
（空きは 77KB あるが最大ブロックが 31KB しかない）。取れなくても
起動は続く（遡れなくなるだけ）。行数は `main.c` の `SCROLLBACK_LINES`。

#### 実機で見つけたこと

**エディタの中で `Shift+PgUp` を押すと画面が壊れた。** 代替画面の上に
主画面の履歴が描かれる。積むほうは `alt_active` を見ていたのに、
**遡るほう（`cdk_term_view_scroll`）で見落としていた。**
0 を返すようにして、呼び出し側がキーを消費せず下へ流せるようにした。

ホストのテストでは出なかった。積む条件ばかり考えて、
「代替画面で遡ろうとしたらどうなるか」を試していなかったため。

#### 検証

`test_term` に 13 ケース、`test_screen` に 4 ケース。
**どちらも、守っている条件を 1 つずつわざと外して落ちることを確かめた**
（履歴側 4 つ、描画側 3 つ）。`wasm_natives_checked` が「0 個 対 0 個」で
通っていた前例があるので、新しい検査は書いた直後に壊してみる。

> **`test_screen` の `count_color` は字の形を見分けられない。**
> どの字でも前景 60 / 背景 12 を返す（'A' も '2' も '4' も同じ）。
> 既存のケースが通っているのは「0 より大きい」までしか見ていないから。
> スクロールバックのケースは**「空白か、何か描かれているか」**で見ている
> （空白セルは背景色ちょうど 72 画素になるので、そこは確実）。
> 字の違いを当てにしたテストを書くと空振りするので注意。

実機:

| 見たこと | 証拠 |
|---|---|
| あふれた出力を遡れる。帯に `^11` | `sb_up.png` |
| 履歴に色と修飾が残る（起動バナーの色） | `sb_up3.png` |
| 履歴の長さで頭打ちになる | `sb_up3.png` |
| 何か打つと最下部へ戻る | `sb_typed.png` |
| エディタでは効かず、画面も壊れない | `sb_edit.png` |
| エディタを抜けても履歴が残っている | `sb_after_edit.png` |

#### やっていないこと

- 履歴の検索（`less` の `/` に当たるもの）
- マウスやタッチでのスクロール
- 履歴を SD に書き出すこと
- 代替画面の履歴
- 行数の実行時変更（起動時に確保する規約を崩さない）

## 7. 入力

### 7.1 キーイベント

```c
typedef struct {
    uint16_t keycode;   // HID usage 相当
    uint8_t  mods;      // ctrl / shift / alt / gui
    uint32_t codepoint; // 文字が確定するなら Unicode、無ければ 0
} cdk_key_event_t;
```

入力源（シリアル注入 / USB HID / 将来の BLE）はすべてこの型に正規化してキューへ。

### 7.2 レイヤ構成

```
入力源 → キーイベント → [SKK レイヤ] → [端末エンコーダ] → バイト列 → SSH / シェル / エディタ
```

SKK が OFF のときはレイヤを素通りする。端末エンコーダは
カーソルキー → `ESC[A`、Ctrl+文字 → 制御コード、Alt+文字 → `ESC` + 文字、
テンキー、F1-F12 (`ESC[11~` 系) を担当。

### 7.3 USB キーボード（最終ハード）

**ESP32-S3 の USB PHY は 1 つしか無い。** USB ホスト（キーボード）と USB-CDC コンソールは
同時に使えない。したがって最終ハードでは:

- USB = ホスト固定（キーボード用）
- デバッグコンソール = UART に出す（ピンヘッダを必ず出しておくこと）

試作段階では USB = デバイス（USB-Serial-JTAG）のまま。
コンソール出力先は `port_link` の背後に抽象化し、ビルド時に切り替える。

内蔵 USB ホストは `usb/usb_host` + HID クラスドライバ（`espressif/usb_host_hid`）を使う。
バスパワー給電が必要なので、最終ハードには 5V を VBUS に流す回路が要る（電源設計の宿題）。

### 7.4 キー配列

US 配列と JIS 配列の両方の変換表を持ち、実行時に切り替える（`set keymap jis`）。
どちらか一方に決め打ちしない。

## 8. ネットワークと SSH

### 8.1 WiFi

`esp_wifi` STA モード。認証情報は NVS に保存し、シェルの `wifi` コマンドで設定。
**ソースにも sdkconfig にも書かない**（ABOUT.md に平文で載っている PSK / SSH パスワードは
テスト用と理解しているが、ファームには焼かない）。

#### 接続は待たない (2026-09-03)

`cdk_wifi_connect_start()` は繋ぎに行くだけで**すぐ返る**。結果は
メインループが `cdk_wifi_poll()` で受け取る。**待つ版は置いていない。**

それまでは起動時に IP が取れるまで最大 20 秒ブロックしていた。AP が居ない
場所（外、電車、別の家）で電源を入れると、その 20 秒はバナーが出たまま
キーも効かず、電源を切る以外に手が無い。**この機械の主目的は SSH だが、
副目的は「持ち出して文字を打つ」で、そちらは WiFi が要らない。**
繋がるまで打てないのは筋が通らない。

途中の状態は**ステータス帯**に出す。IP が取れていれば IP、繋ぎに行っている
最中は「WiFi接続中」、どちらでもなければ「WiFi--」。
帯に出すので、SSH 先や `edit` の画面に居ても分かる。

状態は 4 つ (`cdk_wifi_state_t`)。**「諦める期限を持つか」で 2 種類の
繋ぎ方を分けている。**

| | 期限 | 諦めたら | 使うところ |
|---|---|---|---|
| 最初の接続 | 20 秒 | `FAILED`。人に知らせる | 起動時 / `wifi connect` |
| 確立後の切断 | なし | 諦めない | 電波が切れたとき |

後者に期限を入れると、電波が戻っても繋がらない機械になる。前者から期限を
外すと、SSID を打ち間違えたときに永久に「接続中」のままになる。

#### 諦めさせる口 — `wifi off` (2026-09-03)

「確立後は諦めない」の裏で、**相手が二度と現れない場合に止める手が無い**
という穴が空いていた。家で使っていて点けたまま外へ出ると、この機械は
消えた AP を延々と探し続ける。持ち歩く機械なので、減るのは電池だけ。

`cdk_wifi_off()` が状態を `IDLE` に落として `esp_wifi_stop()` まで行く。
**電波を止めるところまでやるのが要点**で、繋ぎ直しをやめるだけでは
電池の話が解決しない。`IDLE` はイベント側のどちらの枝にも当たらないので、
`disconnect` / `stop` が上げるイベントで繋ぎ直しが再開することもない。

**この場かぎりにしてある。** NVS には書かないので、次に電源を入れれば
普通に繋ぎに行く。設定として残すと「家で電源を入れたのに繋がらない」を
自分で仕込むことになる。戻すのは `wifi connect`。

帯は `WiFi--` のまま増やしていない。**`WiFi--` は一貫して「繋がって
いない。自分では戻らない」**を意味し（諦めた / 止めた / 未設定のどれでも
人がやることは `wifi connect` で同じ）、区別しても打つ命令が変わらない。

イベントは「切れた」ことしか教えてくれないので、AP が応答も切断も返さない
場合は誰かが時計を見ないと `CONNECTING` のまま止まる。**時間切れを見るのは
`cdk_wifi_poll()` だけ**で、だから getter ではなく poll という名前にしている。

#### 繋ぎに行く道は 1 本だけ (不具合 #60)

**`esp_wifi_start()` は 2 回目以降も `ESP_OK` を返す**（冪等）。
`ESP_ERR_WIFI_NOT_STOPPED` ではない。

ここを取り違えて「`ESP_OK` なら `STA_START` イベントが繋ぎに行ってくれる」と
書いていた。`STA_START` は**最初の 1 回しか上がらない**ので、起動時の接続だけ
成功し、2 回目以降の `wifi connect` は誰も `esp_wifi_connect()` を呼ばないまま
20 秒待って `reason=0` で失敗していた。**ドライバは何もしていないのでログにも
一切出ず**、「黙って繋がらない」としか見えない。

起動が非同期になって `wifi connect` を叩き直す経路が普通になったので、
実機で踏んだ（存在しない SSID で失敗させ、正しい SSID に直しても戻れない）。

直し方は**イベント頼みをやめること**。`STA_START` では何もせず、
`cdk_wifi_connect_start()` が start のあと必ず自分で `esp_wifi_connect()` を
呼び、戻り値も見る。繋ぎに行く道が 1 本になり、「誰かが呼んでくれるはず」が
消える。

#### 後から届く知らせは打ちかけの行を壊さない

接続結果はシェルのプロンプトが出たあとに届く。素の `printf` で割り込むと
プロンプトと入力中の文字の間に挟まって、何を打っていたか分からなくなる。
`cdk_shell_notify()` が行頭へ戻して消し、知らせを出してからプロンプトと
行を描き直す（`test_shell.c`「割り込みの知らせは打ちかけの行を残す」）。

シェルに居ないとき（SSH / `edit` / `wasm run`）は**何も書かない**。
向こうの画面が壊れるので、状態は帯だけで伝える。

### 8.2 SSH クライアント — libssh2 に決定 (2026-08-27)

**採用: libssh2 1.11.1 + mbedTLS。** `components_port/libssh2/` にベンダリング済み。
実機で `libssh2_init()` まで通ることを確認済み。

当初は導入コストの低さから wolfSSH を第一候補にしていたが、
実際に調べた結果 **クライアント側 PTY が使えない** ことが分かったので覆した。

#### wolfSSH を採らなかった理由

| # | 事実 | 影響 |
|---|---|---|
| 1 | PTY 要求 `SendChannelTerminalRequest()` が `#if defined(WOLFSSH_TERM) && !defined(NO_FILESYSTEM)` の中にある（`src/internal.c:15995`） | 条件を満たさないと関数ごと消える |
| 2 | ベンダー純正の ESP32 用 `user_settings.h` が **`NO_FILESYSTEM` を定義**している（439 行目） | 既定では PTY 要求がコンパイルされない |
| 3 | 上書き手段は wolfSSL の `user_settings.h` をプロジェクト側で丸ごと抱えることだけ | コンポーネント更新のたびに衝突する |
| 4 | 有効化しても `GetTerminalInfo()` が非 POSIX ターゲットでは **80x24 と "xterm" をハードコード**（`src/internal.c:16231`） | 実機は 53x20。`wolfSSH_ChangeTerminalSize()` で後追い修正が要る |

PTY は「Claude Code / Codex の CLI が動く」という目標に対して譲れない。
`libssh2_channel_request_pty_ex(ch, "xterm-256color", 14, NULL, 0, cols, rows, 0, 0)` は
端末名もサイズも引数で受け取るので、回避策なしで正しい値を渡せる。

GPLv3 の許容は不要になった（libssh2 は BSD-3-Clause）。

#### ベンダリングの方針

コンポーネントレジストリに libssh2 は無いので上流の配布物を取り込む。
`components_port/libssh2/README.md` に版・入手元・更新手順を書いてある。

- ビルド対象は上流 `src/Makefile.inc` の `CSOURCES` のみ。
- **`upstream/src/` からファイルを削らないこと。** `agent.c` は `agent_win.c` を
  **無条件に** `#include` し、`crypto.c` はバックエンドの `.c` を `#include` する。
  中身側で `#ifdef` 分岐しているので、消すとビルドが壊れる。
- 設定は `libssh2_config.h`（`HAVE_CONFIG_H` 経由で `libssh2_setup.h` が読む）。
  **`HAVE_POLL` は定義しないこと。** lwIP / newlib に `poll.h` は無い。`select` を使う。

#### M2 で実装するもの

- 鍵交換 `curve25519-sha256`、ホスト鍵 `ssh-ed25519` / `rsa-sha2-256`
- 暗号 `aes128-ctr`（ESP32-S3 のハード AES が効く）/ `chacha20-poly1305`
- `libssh2_channel_request_pty_ex()` に `cdk_term` の実際の `cols` / `rows` を渡す。
  **80x26 ではなく試作機の 53x20。** 固定値を書かないこと。
- `libssh2_channel_request_pty_size_ex()` で画面サイズ変更を通知
- ノンブロッキング + `select` でメインループに組み込む

**ホスト鍵検証** (`port_knownhosts.c`、M4 で実装): `/sdcard/ssh/known_hosts` と
突き合わせる。方針は TOFU。

| 判定 | 動作 |
|---|---|
| 一致 | 繋ぐ |
| 未登録 | 指紋を出して覚え、繋ぐ (TOFU) |
| **不一致** | **`ESP_ERR_INVALID_STATE` で断る** |
| SD 無し / 書けない | 覚えられないが繋ぐ |

不一致を警告だけにして繋いだら、検証している意味がなくなる。
逆に SD が無いだけで繋げないのは端末として使えないので、そこは緩める。

`hostkey forget` で記録を消せる。これが無いと、正当な再鍵をしたサーバーに
二度と繋げなくなって詰む。

**この「断る」枝は外から普通に叩けない。** 一度も走らせないまま正しいと
信じることになるので、`CDK_KNOWNHOSTS_FAULT_INJECT` を用意した。

```
idf.py build -DCDK_FAULT_KNOWNHOSTS=1     # 照合用の鍵の末尾ビットを反転する
```

**壊すのは照合に使う鍵だけで、記録には本物を書く。** 両方壊すと、
記録も同じように壊れて一致してしまい「細工したのに繋がる」ことになる
（実際に一度これで引っかかった）。照合だけ壊せば 1 つのビルドで

1. 1 回目 — 未登録なので本物を記録して繋がる
2. 2 回目以降 — 記録（本物）と照合用（壊れている）が食い違うので必ず断る

まで通せる。既定は無効で、有効にすると CMake が警告を出す。
CMake のキャッシュ変数なので、**確認が済んだら `-DCDK_FAULT_KNOWNHOSTS=0`
で戻して、実際に繋がるところまで見ること。**

libssh2 の鍵種別は曲線ごとに別のビットに直すこと。
ECDSA をまとめて `LIBSSH2_KNOWNHOST_KEY_ECDSA_256` にすると、
nistp384 の鍵を `ecdsa-sha2-nistp256` という嘘の名前で書き出してしまう。

#### タスク構成

SSH の受信は**メインループが `select` で他と一緒にポーリングする**。
専用タスク + キューにはしない。M2 の規模では単純さが勝るため。

この選択は M4 で効いてくる。SD と LCD が SPI3 を共有するので、
キャンバスへの描画と SD アクセスを直列化するミューテックスが要る。
描画がメインループ内で完結していれば、ロックはそこ 1 箇所で済む。

#### 繋ぐところを 2 つに割る (2026-09-03)

`scp` がハンドシェイクと認証を**使い回す**ために、`cdk_ssh_connect()` を
2 つに割った。

| | やること |
|---|---|
| `cdk_ssh_session_open()` | TCP・ハンドシェイク・known_hosts・認証まで |
| `cdk_ssh_shell_open()` | PTY 付きチャネルを開いてノンブロッキングへ |

**認証の塊を写さないため。** あそこには「空パスワードで password 認証を
叩かない」「`.pub` を必ず渡す」「ホスト鍵が食い違ったら断る」が入っていて、
どれも実機で踏んだ末のもの。2 つ持つと片方が腐る。

`cols` / `rows` は PTY にしか要らないので、認証に要るものだけを
`cdk_ssh_login_t` に分けた。`scp` に意味のない桁数を渡させない。

##### `connect()` に期限を入れた

`CONFIG_LWIP_TCP_SYNMAXRTX=12` なので、**居ない IP へブロッキングで
`connect()` すると SYN の再送が終わるまで分単位で戻らない。** その間
メインループが止まり、画面もキーも死ぬ。ノンブロッキング connect ＋
`select()` で **8 秒**に切った。

**`libssh2_session_set_timeout()` では防げない。** あれは libssh2 自身の
呼び出しにしか効かず、その手前の TCP には届かない。元からあった穴で、
打ち間違えたホストで `ssh` が数分固まっていた。実機で 8 秒に収まることと、
画面に `192.168.1.231 に届きません` が出ることを確認した。

##### 期限は入れたら**戻す**

接続と認証の間は `libssh2_session_set_timeout()` を 10 秒にする。
**ノンブロッキングへ切り替える前に 0 へ戻すこと。**

戻さないと、何も来ていないときの `libssh2_channel_read` が EAGAIN では
なく `LIBSSH2_ERROR_TIMEOUT` を返す。`cdk_ssh_read` はそれを通信断として
扱うので、**10 秒黙っていただけのセッションが切れて再接続が走る。**
継ぎ目を切る作業で既存の `ssh` を壊す唯一の道がここだった
（実機で 25 秒放置して切れないことを確認した）。

##### 不具合 #61 — 切断のたびに fd が漏れていた

「開いているセッションを黙って壊さない」判定を `cdk_ssh_session_open()` に
足したら、`exit` したあとの再接続が `ESP_ERR_INVALID_STATE` で通らなく
なった。追ってみると**元からあった漏れ**だった。

リモートが `exit` すると `cdk_ssh_read` は `s_open` を false にするだけで、
セッションもソケットも解放しない。従来の `cdk_ssh_connect` は
`if (s_open)` でしか閉じないので、**残った `s_session` / `s_sock` を黙って
上書きしていた** — 切断と再接続を繰り返すたびに fd と libssh2 の
セッションが漏れる。`s_open || s_session != NULL || s_sock >= 0` で
閉じるように直した。

### 8.3 `ssh user@host` と溜めたパスワードの範囲 (2026-09-03)

Linux と同じ `ssh alice@example.com` で繋げる。**NVS には書かない**
（その場かぎり。覚えさせたいなら `set ssh.host` / `set ssh.user`）。

#### 溜めたパスワードは、溜めた相手にしか送らない

**`ssh.pass` は `ssh.host` の `ssh.user` のものであって、「どこでも使う
合言葉」ではない。** 引数で渡された相手へ黙って送ると、宛先を打ち間違え
ただけで、知らない機械に平文のパスワードを渡すことになる。**送ってしまった
ものは取り消せない。**

そこで、引数の **ユーザーもホストも NVS の値と一致するときだけ**溜めた
パスワードを使う。それ以外は鍵だけで行く（`password` には `""` を渡す。
`NULL` は `libssh2_userauth_password` が `strlen()` に素通しするので落ちる）。

| 打ったもの | パスワード | 鍵 |
|---|---|---|
| `ssh` | 使う | 使う |
| `ssh <NVS と同じ user@host>` | 使う | 使う |
| `ssh <それ以外>` | **使わない**（鍵が駄目なら §8.5 で聞く） | 使う |
| `ssh <その場で打った相手と同じ>` | 使う（打ってもらったもの） | 使う |

この機械は SD の鍵で入るのが本筋なので、実用上もこれで足りる。
鍵だけで行くときは「（鍵のみ）」と出す。**黙って行くと、入れなかったときに
パスワードの問題だと思って見当違いのところを直しに行く。**

同じ理由で、パスワードが空のときは `password` / `keyboard-interactive` を
**叩かない**。sshd の試行回数を無駄にするし、失敗理由が「password 認証に
失敗」になって嘘をつく。

#### 繋ぎ直しは「引数で渡した相手」へ戻る

指定した相手は `s_ssh_arg_*` に残り、**切断や失敗では消えない。消すのは
引数なしの `ssh` だけ。** 閉じるたびに消すと、`ssh alice@box` のセッションが
落ちたあとに NVS の既定へ繋ぎ直してしまう。**別の機械に入る**ので、
ここはいちばんやってはいけない間違い。

#### 引数を黙って無視しない

`user@host` として読めない引数は断る（`ssh myhost` を含む）。それまでは
`close|key|keygen` 以外の argv[1] を素通しして NVS の相手へ繋いでいたが、
**引数が意味を持つようになったので、黙って別の相手へ繋ぐのは以前より悪い。**

分解は `cdk_shell_split_userhost()`。ホスト側でテストできるように
`cdk_shell` に置いてある（`cdk_shell_split` と同じ扱い）。区切りは
**最後の `@`**（Linux と同じ）。片方が空・長すぎるときは何も書かずに
false を返す。**半端に埋めると、呼び側が「ユーザーだけ取れた」と誤解して
知らない相手へ繋ぎに行く。**

### 8.4 `scp` — ファイルを 1 本やり取りする (2026-09-03)

```
scp <手元> user@host:<パス>     送る
scp user@host:<パス> <手元>     取る
```

それまで手元と向こうでファイルを渡す手段は `cdk.py push`（**PC から** SD へ）
と SSH 越しに `cat` して目で写すことだけで、**この機械だけで完結した経路が
無かった。**

`-r` も複数指定もやらない（人間の指定）。1 本ずつ。

#### SFTP ではなく SCP

`scp.c` も `sftp.c` も上流の `CSOURCES` をそのまま並べているので**最初から
ビルドに入っていた**（ベンダリングの方針の副産物で、誰も狙っていない）。
1 本ずつ運ぶだけなら SCP のほうが軽い — SFTP は 1 ファイルあたり 4KB の
ハンドルと 256KB のパケット上限を持ち歩く。

**代わりに相手側に `scp` の実行ファイルが要る。** OpenSSH 9 以降は `scp`
コマンド自身が中で SFTP を使うようになったが、サーバー側の `scp` バイナリは
今も入っているので通る。`sftp-only` に絞った相手では通らない。そのときは
`libssh2_sftp_*` へ移せる。

#### 転送はメインループが刻む。専用タスクは作らない

| | どうするか |
|---|---|
| 接続・認証（約 1.9 秒） | **待つ**。既存 `ssh` と同じ（§8.2 の判断をそのまま使う） |
| 転送本体 | **メインループが `cdk_scp_poll()` で刻む** |
| シェル | 転送中は止める (`SESSION_SCP`) |

刻むので画面もキーも `cdk_link_poll` も生きたまま。**転送中に `cdk.py shot`
が撮れることを実機で確かめた**（進捗行が写る）。これが `wasm run` のように
専用タスクを作らなくて済む理由で、1 周で動かす量をこちらが決められるから。

##### それでもシェルは止める

**FATFS の空きハンドルは本体に 1 本しか無い**（`max_files=5` のうち 4 本は
`CDK_WASM_FILES_MAX` が予約）。背景で転送しながらシェルを使えるようにすると

- 転送がその 1 本を握っている間、`edit` / `cat` / `sdtest` が開けない
- 転送中に `ssh` を叩くと `cdk_ssh_connect()` が `cdk_ssh_close()` を呼び、
  **scp のセッションを黙って壊す**（セッションは static 1 組しかない）

止めておけば、この事故が「起きにくい」ではなく**起きない**。
`wasm run` が同じ理由で同じ判断をしている。

Ctrl-C は `route_key` と **`route_bytes` の 2 か所**に入れる。
後者を忘れると `cdk.py key ctrl+c` が黙って効かない（制御チャネルの
バイト列は `route_key` を通らない）。

#### 踏んだ罠

##### セッションとソケットは**両方**切り替える

`libssh2_session_set_blocking(sess, 0)` だけではノンブロッキングにならない。
**ソケットが blocking のままだと libssh2 の `recv()` がカーネルの中で待つ**
ので EAGAIN が返らず、メインループが止まる。実機では「転送は始まるのに
`cdk.py shot` が `SHOT_INFO が返りません` で落ちる」という形で出た。
`cdk_ssh_go_nonblocking()` に 1 か所へまとめて、`ssh` の側もそれを使う。

##### 「不一致」と「二重呼び出し」を同じ型で返さない

`cdk_ssh_session_open()` はホスト鍵の不一致で `ESP_ERR_INVALID_STATE` を
返す。二重呼び出しの判定にも同じ型を使ったところ、`exit` のあとに残った
セッションが原因で **繋がる相手に「ホスト鍵が記録と一致しません」と
表示された。** 直し方を探させる方向が完全に間違う。
後者は `ESP_ERR_NOT_FINISHED` に分けた。

##### 送信の終端手続きは省けない

中身を送り切ったら **NUL を 1 個送り、相手の返事を 1 個読み、
`send_eof` → `wait_eof` → `wait_closed`**。省くと相手側が確定せず、
中身が切れたファイルや 0 バイトが届く。

返事が 0 以外なら、**続けて流れてくるメッセージを読んで理由にする。**
実機で最初に出たのは `scp: /tmp/from_deck.txt: No space left on device`
（相手のディスクが 100% だった）。「断られました」だけでは何を直せばいいか
分からない。

##### 受信は `st_size` ちょうどで読み終える

1 バイトでも余分に読むと、枠組みの終端待ちで固まる。
実機で `受信 315904/315904 バイト` と一致することを確かめた。

##### 相手のパスを引用しない

libssh2 は `quote_paths` が既定で 1 なので**中で shell quote する**。
こちらで括ると二重になって、引用符ごとの名前のファイルができる。

#### 実測（この相手は国外の VPS）

| | |
|---|---|
| 316KB の受信 | 13 秒（約 24KB/s） |
| 1 周 1 回 → 8 回に増やした効果 | **無し**（どちらも 13 秒） |

網の往復が支配していて、メインループの刻み (5ms) は上限になっていない。
LAN の相手なら 8 回が効くはずだが**確かめていない**。

~~上限は 512KB (`CDK_SCP_MAX_BYTES`)~~ → **2026-09-17 に撤廃**（人間の指定。
`wget` と同じ扱い）。SD が埋まれば書き込みの失敗で止まり、`.tmp` を消す。

#### 4GB 超の受信は、終わってからしか分からない

**この機械の `off_t` は 32 ビットの `long`。** libssh2 は相手の申告を
64 ビット（`scpRecv_size`）で読むが、`libssh2_struct_stat` の `st_size`
（= `off_t`）に詰めるときに上が落ちる。

- 2GB〜4GB は負で来る → `(uint32_t)` で読み直せば正しい（FAT の上限も 4GB）
- 4GB 超は下 32 ビットだけ残る。4GB+1KB は **1024 バイト**として来る

libssh2 の内部構造体は触らない（ベンダリングは無改造が方針）。代わりに、
申告どおり読み終えたところで **scp の終端（NUL 1 個）** を読み、さらに
**300ms 続きが来ないこと**を確かめる。正しい転送なら相手の `scp` は終端を
送ってこちらの応答を待つので、何も来ない。

NUL を確かめるだけでは足りない。**切られた申告の直後が中身の 0 バイト**だと
すり抜ける。疎なファイル（`truncate -s`）なら必ずそうなるし、実機の確認も
それで行った。

送信側は問題ない。手元は FAT なので 4GB 未満が保証され、`stat` の負の値も
`(uint32_t)` で読み直す。進捗の百分率は `done * 100` が 43MB で 32 ビットを
溢れるので 64 ビットで掛ける。

実機で確かめた（2026-09-17・相手の VPS はディスクが満杯だったので疎なファイルで）:
1MB の受信（旧上限超え、約 25KB/s で 41 秒）、4GB+1KB → 「大きすぎます (4GB 超)」
で `.tmp` も残らない、3GB の受信が合計 3000000000 バイトで始まり `0%` 表示の
まま Ctrl-C で止まる、1MB の送信が全部送れて相手の「No space left on device」
がそのまま出る。**送信の成功（512KB 超）は相手の空きが無く確かめていない。**

行き詰まりは 30 秒で諦める — 相手が黙ると EAGAIN が永久に返るので、
誰かが時計を見ないと終わらない。

### 8.5 その場でパスワードを聞く (2026-09-04)

`ssh alice@box` は §8.3 の通り鍵だけで行く。鍵が相手の
`authorized_keys` に無ければそこで終わりで、**知らない機械に入る手段が
無かった**（`set ssh.host` / `ssh.user` / `ssh.pass` を 3 つ書き換えて
NVS の相手そのものを差し替えるしかない。戻すのを忘れると、次の `ssh` が
別の機械へ行く）。

そこで **鍵で断られたときだけ**パスワードを聞く。

```
$ ssh nobody@203.0.113.10
ssh   : nobody@203.0.113.10 に接続中（鍵のみ）...
ssh   : 鍵では入れませんでした
nobody@203.0.113.10 のパスワード: *******
```

#### 聞くのは鍵が駄目だったあと。先には聞かない

先に聞くと、**鍵で入れる相手にまで平文の合言葉を打たせる**ことになる。
この機械は SD の鍵で入るのが本筋（§8.3）なので、順序が逆になると
本筋のほうが面倒になる。

繋ぎ直し（`cdk_retry`）では聞かない。`app_ssh_open(bool interactive)` の
引数で分ける。**誰も見ていない画面で聞いても答えは来ない**し、聞いている
間シェルが伏せ字のまま止まる。

#### 打ってもらったものも「打った相手」にしか送らない

§8.3 の規則をそのまま当てる。`s_ask_user` / `s_ask_host` / `s_ask_pass` の
**3 つで 1 組**にして、`pick_password()` が相手ごと突き合わせる。
パスワードだけ持つと、次に別の機械へ繋ぐときに黙って送ってしまう。

判定は `pick_password()` 1 か所のまま（`ssh` と `scp` で共有）。出どころを
`pass_src_t` で返すようにした。**どれを送ったかで、失敗したときの言い方も
次にすることも変わる**から:

| 出どころ | 失敗したときに出すもの | そのあと |
|---|---|---|
| `PASS_NONE`（鍵だけ） | 「鍵では入れませんでした」 | **聞く** |
| `PASS_NVS` | 「認証に失敗（鍵もパスワードも通りません）」 | そのまま |
| `PASS_ASKED` | 同上 | **忘れる** |

**通らなかったものを忘れるのが肝。** 残すと `pick_password()` が持って
いる限り `PASS_NONE` にならないので、次の `ssh` も同じ間違ったパスワードで
黙って落ちて、**打ち直す道が無くなる**。忘れておけば、もう一度 `ssh` と
打てばまた聞く。

空の `ssh.pass` も「無い」と同じ扱いにした。空を持っていることにすると
「（鍵のみ）」が出ず、`set ssh.pass ""` の相手で聞く道にも入らない。

#### 消えかた

| きっかけ | 消える？ |
|---|---|
| 電源を切る / `reboot` | 消える（NVS には書かない） |
| `ssh forget` | 消える（**人に貸す前に押せる口**） |
| 引数なしの `ssh` | 消える（宛先を戻すのと一緒に） |
| 切断・繋ぎ直し・`ssh close` | **消えない**（同じ相手へ戻るのに要る） |

`ssh forget` は NVS の `ssh.pass` を消さない。あれは `set` の持ち物で、
**消したつもりが設定ごと消えていた**が起きるとつらい（消すなら
`set ssh.pass ""`）。

#### 伏せ字の入力は `cdk_shell_ask()`

行編集の器はコマンド行と同じものを使い回す。**2 つ持たない**（分けると
伏せ字の側だけ UTF-8 の削除や桁数の数え方を間違える）。違うのは
「何を描くか」と「どのキーを通すか」だけ:

- 画面には `*` しか出さない。出口は `redraw()` 1 か所なので、
  **WiFi の知らせ（`cdk_shell_notify`）が割り込んで描き直しても漏れない。**
  字数は出す（`set` がパスワードの文字数だけ出すのと同じ考え。何文字
  打てたか分からないと打ち直しの判断ができない）。
- **履歴に積まない。補完もカーソル移動も通さない。** 履歴や候補一覧に
  合言葉が出る。カーソル移動を許さないのは `*` の下のどこに居るのかを
  見せられないから。通すのは「打つ・1 文字消す (BS)・全部消す (Ctrl-U)・
  出す (Enter)・やめる (Ctrl-C / Esc)」だけ。
- **入れ物に入らない長さは切り詰めずに断る。** 途中まで合っている合言葉を
  送っても通らないし、「打ったのに違うと言われる」の原因が分からない。
- 空の Enter は「やめた」。port 側は空文字を「パスワード無し」と見るので
  （§8.3）、渡しても認証を叩かずに落ちるだけになる。
- `cdk_shell_begin()` / `cdk_shell_end()` は聞くのをやめる（cb は呼ばない）。
  SSH が切れて戻ってきたシェルが伏せ字のまま待ち続けるのを防ぐ。

**日本語入力は通さない。** `route_key` で SKK より先に伏せ字を見る。
かな入力のままだと `pass` が「ぱっｓ」になって送られるし、変換中の `▽` に
打った字がそのまま出る（伏せ字にならない）。

答えは `cdk_shell_key()` の中から cb で返る。**そこで SSH を張ってよい**
（`ssh` コマンドが呼ばれるのと同じ場所・同じタスク。張れたら
`cdk_shell_end()` されるだけ）。

#### `scp` では聞かない

転送はメインループが刻むので、途中でシェルに戻って伏せ字を出す道が無い。
先に `ssh` で入っておけば、その相手のぶんは `pick_password()` が覚えている
ので `scp` もそれで通る。

#### やっていないこと

**相手が `password` を出していないときも、いちど聞いてしまう。**
`PasswordAuthentication no` の sshd では、打ってもらっても port 層が
「サーバーが出していない方式は叩かない」（§8.3）ので送られず、
「認証に失敗（鍵もパスワードも通りません）」と出る — **パスワードは
試していないのに、そう読める。** 聞く前に方式を見るには
`libssh2_userauth_list()` の結果を port 層から取り出す口が要る。
1 回聞かれるだけで繰り返しはしないので、いまは断らずに置く。

#### 実機で確かめたこと (2026-09-04)

相手は国外の VPS（`203.0.113.10`）。鍵の入っていない `nobody` で叩いた。

| | |
|---|---|
| 鍵で断られる → 聞く | ✅ 「（鍵のみ）」→「鍵では入れませんでした」→ 伏せ字 |
| 打った字 | ✅ `*` だけ。7 文字打って `*` 7 つ |
| 間違ったパスワード | ✅ 「認証に失敗（鍵もパスワードも通りません）」 |
| そのあともう一度 `ssh` | ✅ また「（鍵のみ）」から始まって聞き直す（忘れている） |
| Ctrl-C | ✅ `^C` を出して「やめました」。シェルに戻る |
| `ssh forget` → 引数なしの `ssh` | ✅ NVS の相手へ今まで通り入れる |

## 9. SKK 日本語入力

### 9.1 辞書

**使うのは `SKK-JISYO.L.unannotated`**（注釈なしの版）。EUC-JP のテキストで
4.1MB。デバイス上でパースしない。`tools/skk_build.py` で PC 側でバイナリ化する:

```
ヘッダ 32 バイト   "SKKD" / version / flags / 件数 / 各領域のオフセット
索引               u32 × (送りあり + 送りなし)  レコード領域の先頭からの相対
レコード           "見出し語\0候補列\0" の並び。候補列は "/候補1/候補2;注釈/"
```

- **送り仮名あり / なしを別の索引にする。** 一緒くたにすると「おくr」のような
  送りあり見出しが普通の見出しと並び、送り仮名変換が静かに壊れる。
  取り違えても「見つからない」ではなく**別の語が引ける**ので気づきにくい。
- **見出し語は UTF-8 バイト順に並べ直す。** 元の辞書は EUC-JP 順なので、
  そのままでは `memcmp` による二分探索が成立しない。
- 読み出しは**コールバック経由** (`cdk_skk_read_fn`)。フラッシュ
  (`esp_partition_read`)、SD 上のファイル (`fread`)、ホストのテスト
  （メモリ）で読み方が違うのに探索の理屈は同じだから。`FILE*` を
  直接受ける設計にすると実機で使えない。
- RAM 使用量は辞書の大きさに依存しない。17.5 万件で 1 回の検索が
  索引 18 回 + 見出し 18 回の読み出しで済む。

**配置**（`cdk_skkdict_open` はこの順に探す）:

1. microSD `/sdcard/skk/SKK-JISYO.bin`（差し替えが容易なので優先）
2. フラッシュの `skkdict` パーティション（**L 全体が入る**）

当初は「フラッシュには SKK-JISYO.M 相当の縮小版」と考えていたが、
実測でバイナリが 4MB に収まらないと分かったので `skkdict` を 8MB に広げて
全部載せることにした。SD 上のファイルは実機にカードを挿さないと
用意できず、開発の回し方に直結するため。M（6,934 語）では実用にならない。

#### 注釈を落とす

**`SKK-JISYO.L.unannotated` を使う。**

| | 語彙 | バイナリ |
|---|---|---|
| `SKK-JISYO.L` | 送りあり 15,996 / 送りなし 159,795 | 6,857,578 バイト |
| `SKK-JISYO.L.unannotated` | **同じ** | **6,319,076 バイト** |

**語彙は 1 語も減らない。**候補に付く説明文（`藍;植物` の `;植物`）が
無いだけで、538KB 小さくなる。53 桁 20 行の画面では注釈を出す余地が
そもそも少なく、`skkdict` コマンドで引いたときに出る程度だった。

注釈つきで焼きたければ `SKK-JISYO.L` をそのまま渡せばよい。形式も
`cdk_skk_cand_at` の注釈の切り離しもそのまま残してある。
**8MB に広げた判断は変わらない**（注釈を落としても 4MB には収まらない）。

ヘッダの注釈フラグは「注釈を残す設定でビルドしたか」ではなく
**実際に注釈が入っているか**を表す。最初から注釈の無い辞書を
`--no-annotations` なしでビルドしたときに「注釈あり」と名乗らないため。

```
python tools/cdk.py dict SKK-JISYO.L.unannotated               # 変換してフラッシュへ焼く
python tools/cdk.py dict SKK-JISYO.L.unannotated --build-only  # 大きさだけ見る
```

焼き先はビルド済みのパーティション表から引く。`0x410000` を決め打ちに
すると、`partitions.csv` を直した瞬間に「焼けたのに読めない」という
分かりにくい壊れ方をする。

### 9.2 エンジン

`components/cdk_skk/` は純 C。「キーイベント → 確定した文字列 + 表示状態」の
関数として書いてあるので、実機に載せる前にホストで全部テストできる。

| ファイル | 役割 |
|---|---|
| `cdk_skk_romkana.c` | ローマ字 → かな の表と状態機械。カナ / 半角カナ / 全角英数への変換 |
| `cdk_skk_dict.c` | 辞書バイナリの二分探索、候補列の切り出し |
| `cdk_skk.c` | モードと ▽ / ▼ の状態機械 |

**促音は表に直接書く。** `"kk" → っ + 打ち直し "k"`。規則で書こうとすると
「n は重ねても っ にならない」「ch は tch」といった例外が条件分岐で並ぶ。

**撥音だけは表で書けない。** `"nn"` を単に ん と決め打つと `konna` が
「こんあ」になる。2 つ目の n が「ん」なのか「な行の頭」なのかは、
その次の文字を見ないと決まらない。ここだけ後読みする。

```
n  + n         → まだ決めない（"nn" として持つ）
n  + 子音・記号 → ん を確定して打ち直し
nn + 母音・y   → ん + 打ち直し "n"    （konna → こんな）
nn + その他    → ん
```

かなは常にひらがなで出し、モードによる変換は確定時に行う。ここでモードを
持つと表がモードの数だけ増えるうえ、辞書引きは常にひらがなで行うため。

#### キー割り当て

| キー | 動作 |
|---|---|
| `Ctrl-J` | かな入力の開始 / 未確定の確定 / 全英から復帰 |
| `l` | ASCII（SKK を止める） |
| `L` | 全英 |
| `q` | ひらがな ⇄ カタカナ。▽ の中では見出しをカタカナで確定 |
| `/` | abbrev（ローマ字変換せず英字のまま見出しにする） |
| 大文字 | ▽ に入る。▽ の途中でもう一度打つと送り仮名の始まり |
| `Space` | ▽ → 変換、▼ → 次の候補 |
| `x` | ▼ → 前の候補 |
| `ESC` | ▽ を捨てる / ▼ から ▽ へ戻る |

送り仮名は「かな + 送りの頭の子音」で引く（`KaeRu` → `かえr`）。

**`Ctrl-J` はバイト列経由では届かない。** `cdk_keys_decode` は 0x0A を
Enter に潰すので、`cdk.py type` からは送れない。KEY フレーム
（`cdk.py key ctrl+j`）と実機の USB HID では区別できる。シェルからは
`skk on` でも切り替えられるようにしてある。

#### 未確定文字列の表示

**描画は `cdk_screen` の中に置く。** 実機側だけで重ね描きすると、ホストの
基準レンダラが同じ絵を作れなくなり、`shot --verify` の突き合わせから
外れる。▽ ▼ * は `mkfont.py` が半角として自前生成している字なので、
桁ずれが起きるならまさにここ。検証の外に出すわけにいかない。

カーソル位置から反転表示で重ね、右端に収まらないときは左へ寄せる。
折り返すと下の行を潰したうえに復帰が面倒になる。

`cdk.py shot --verify-vt <fixture> --preedit <file>` でホストと突き合わせる。
未確定文字列を引数ではなくファイルで渡すのは、Windows の `main()` が
`argv` を ANSI コードページで渡してきて日本語が壊れるため。

#### 個人辞書（学習）

確定した候補を次から先頭に出す。無いと、よく使う語でも毎回同じ回数
Space を押すことになり、長い文章を書くのが苦痛になる。

`/sdcard/skk/user.dic` に**1 行追記する**。全体を書き直さないのは、
書いている途中で電源が落ちたときに辞書ごと失うのを避けるため。
同じ見出しの行が何度あってもよく、**後の行が勝つ**。

```
# cdk skk user dictionary v1
n<TAB>にほん<TAB>/二本/日本/
a<TAB>かえr<TAB>/代/帰/
```

先頭の `n` / `a` は送りなし / 送りあり。SKK 本来の辞書形式は送りあり /
なしをファイル内の区画で分けるので、追記だけでは育てられない。
行ごとに持つ独自形式にしてある。

引くときは個人辞書が先で、本辞書の同じ候補は落とす。SD が無いときは
RAM 上だけで働かせる（再起動で消えるが、その場かぎりでも打鍵は減る）。

**書き込みは描画の外で行う。** `route_key` → 確定 → 追記 → その後で
`cdk_screen_draw` の順。描画中に SD を触ると LCD と SPI3 を奪い合う。

#### まだやっていないこと

- **辞書登録モード。** 辞書に無い語はいま かな のまま確定する。
  個人辞書に直接書けば引けるので、追加の経路が無いわけではない。
- 数値変換 `#`、候補の一覧表示（いまは 1 つずつ送る）
- 送りありの候補を送り仮名で絞り込む（ddskk の「送り仮名の厳密なマッチ」）

コマンドライン編集は `cdk_shell` に自前実装し、入出力は端末バッファ経由にする
（SSH セッションと同じ土俵に乗せるため）。

コマンド案:

```

### 実装済み (M4 時点)

`uart send <hex|str>`（ワンショット送信）は入れていない。
`ssh <user>@<host>` の引数指定もまだで、いまは設定に入っている 1 か所へ繋ぐだけ。

### シリアル端末 — `uart` (2026-09-12)

```
uart                  外部 UART の端末を開く（115200 8N1・フロー制御なし）
uart 9600             速度を指定する
uart 115200 --flow    RTS/CTS のハードウェアフロー制御を入れる（-f も可）
```

D-sub / Grove に挿した機器と直接話すためのもの。基板側は最初から
用意されていた（SP3232EEN はドライバ 2・レシーバ 2 で TX/RX/RTS/CTS が
ちょうど載り、`cdk_board.h` に 4 本とも定義済み）が、ファーム側は
`cdk_uart_open/read/write/close` が **wasm アプリ専用の貸し出し口**
としてだけ在って、シェルから触る道が無かった。

#### ピンは選ばせない

外に出せる UART は 1 本きり（UART0 = コンソール、UART1 = 制御チャネル）で、
その 1 本の配線先も基板で決まっている。`uart open <tx> <rx>` のように
番号を打たせても、行き先は同じで打ち間違える余地が増えるだけなので、
`CDK_BOARD_EXT_UART_*` で固定した。ピンを選べる口は wasm 側に残っている。

**RTS/CTS はフロー制御を入れたときだけ掴む。** G21/G38 は
HARDWARE_DESIGN.md が「フロー制御を使わないなら空く」と書いているピンで、
常に掴むとその通りにならない。無効時は `UART_PIN_NO_CHANGE` を渡す。

#### 抜けるキーは `Ctrl-] q`

「見送ったもの」（M3）が先に決めろと言っていた 2 点。1 打鍵で抜ける方式だと
**バイナリを流す相手に 0x1D を送れなくなる**ので、前置キーにした。
素の `Ctrl-]` は 0x1D として相手へ通り、`q` を続けたときだけ抜ける。

| | どうするか |
|---|---|
| `Ctrl-] q` | シェルへ戻る |
| `Ctrl-]` + その他 | 0x1D とそのキーを相手へ送る |
| `Ctrl-C` | **横取りしない。**相手へ通す（wasm / scp とは逆） |

`Ctrl-C` を食わないのは、相手の CLI を止める合図がそれしか無いから。
その代わり `cdk.py key ctrl+c` ではこのセッションを抜けられない。

#### 踏んだ罠

##### 前置キーの判定は SKK より前に置く

`route_key` の優先順位は SKK が先で、**かなモードの SKK は素の `q` を食う**
（カタカナ切り替え）。UART の分岐を SKK の後ろに置くと、日本語を打つために
かなにした時点で `Ctrl-] q` が届かず、**画面を占有したまま抜ける手段が
無くなる**。前置の判定だけを SKK の前に出し、2 打目は SKK へ落としている
（そうしないと相手に日本語が打てない）。

##### `uart_write_bytes` はフロー制御で無期限に待つ

`uart_write_bytes` は TX リングが埋まると `portMAX_DELAY` で待つ。
フロー有効で相手の CTS が下がったままだと TX FIFO が永久に捌けない。
wasm から呼んでいた間はアプリ自身のタスクが止まるだけだったが、
**このセッションで書く主体はメインループ**なので、画面・キーボード・
制御チャネルが揃って死に、外から様子を見る手段まで無くなる。

`cdk_uart_write` を「`uart_get_tx_buffer_free_size` で入る分を確かめて、
入らなければ捨てて -1」に変えた。**詰まる理由は 2 つあって、中からは
区別できない**（相手の CTS が浮いている / 単に速度が足りない）。
制御チャネルは 921600 で来るので、`uart 9600` に 1KB 以上貼り付けると
TX リング (1KB) が溢れて後ろが落ちる。溜める口は作っていないので、
通知の文言で原因を決めつけないようにした。DESIGN §8.4 が scp に課しているのと
同じ「メインループを止めない」制約。**詰まりは 1 回だけ画面に出す**
（弾かれるたびに出すと、貼り付け 1 回で画面が警告で埋まる）。
なお wasm 側の `uart_write` には同じ地雷が元から在る。

##### 応答を返す口では `term_printf` を使えない

`on_term_reply`（`CSI 6n` などの応答）は **`cdk_term_feed` の途中から
呼ばれる**。詰まりを知らせる `term_printf` はその `cdk_term_feed` を
また呼ぶので、エスケープ列を解きかけの状態で再入して壊れる。
ここだけは `cdk_uart_write` を直に呼んで、落ちた応答は黙って捨てる。

##### 入力の出どころは 2 つある

`cdk.py key ctrl+]` は MSG_KEY で `route_key` に来るが、
**`cdk.py type` は MSG_TEXT で `route_bytes` に来る**。前置キーの状態機械を
片方にしか入れないと、貼り付けた 0x1D の扱いが食い違う（scp の Ctrl-C が
2 か所に在るのと同じ理由）。

#### 実測（v1 実機・2026-09-12）

| 確かめたこと | 結果 |
|---|---|
| ホスト単体試験 | 27/27（`uart` の引数 5 件・帯 3 件を追加） |
| ビルド | v1 / CoreS3 の両方。CoreS3 は `CDK_BOARD_HAS_EXT_UART 0` で丸ごと落ちる |
| 開く | `[UART2 115200 8N1 flow:OFF]`。帯に `UART 115200` |
| `uart 9600 --flow` | `flow:ON`、帯 `UART 9600 F`。**閾値 122 と RTS=G21 / CTS=G38 を実機のドライバが受けた** |
| `Ctrl-] q` | 戻る（`route_key`） |
| **かなモードで `Ctrl-] q`** | **戻る。** 帯は `UART 9600 あ` で 40 桁に収まる |
| 0x1D + `q` を `cdk.py type` | 戻る（`route_bytes`） |
| `Ctrl-C` | セッションに留まる（相手へ通る） |
| **詰まり** | `uart 9600 --flow` に 2000 バイト流す → **`ping OK` のまま。警告は 1 行だけ** |
| 詰まりの再通知 | 抜けて開き直すと、また出る |
| 開き直し | 何度でも開ける（`cdk_uart_close` が効いている） |
| 引数 | `9600x` `--fast` `300000000` を理由つきで断る |
| 回帰 | `cdk.py selftest` OK（基準画像と完全一致） |

**折り返し（D-sub の先で TXD↔RXD / RTS↔CTS）でも確かめた（2026-09-12）。**

| 確かめたこと | 結果 |
|---|---|
| echo | 打った字がそのまま戻る（ローカルエコーは無いので、見えている物は往復してきたデータ） |
| **フロー制御が効いている証拠** | **CTS が浮いていたときは同じ `--flow` で詰まったのに、RTS↔CTS を繋ぐと流れた。**CTS 入力が RTS で実際に駆動されている |
| 取りこぼし | 9600 `--flow` で 320 バイト、230400 `--flow` で 960 バイト。**番号付き 30 行が順番どおり、欠けも化けも無し** |
| フロー無効との対照 | 230400 フロー無しでも完走。帯も `F` が消える（無効時は G21/G38 を掴まない） |
| 送信リングの上限 | 9600 に 2000 バイトで詰まりの通知。`ping OK` のまま |

**RTS が「絞り込む」ところまでは出せていない。** SP3232 の定格
（〜235kbps）の範囲では ESP32 の受信が余裕で追いつき、RX FIFO が
閾値 122 を超えない。折り返しなので相手も自分で、送る側を待たせる
状況を作れない。**確かめたのは「RTS が出ていて CTS がそれを受けている」**
ことで、**「混んだときに RTS を下げて相手を止める」ことではない。**

**詰まりの試験がこの実装の山だった。** 対策前なら、この 2000 バイトで
メインループごと止まって `ping` も返らなくなっていたはず。

**まだ確かめていないもの:**

- **RTS の絞り込み**（混んだときに RTS を下げて相手を止める）。
  上記のとおり、折り返しでは負荷を作れない。本物の相手が要る
- **wasm が UART を掴んでいるときに `uart` が断ること**
  （`uartecho.wasm` が SD に無く、今回は流していない）

### Web から取る — `wget` (2026-09-16)

```
wget <URL>            URL の末尾の名前で /sdcard に置く
wget <URL> <名前>     名前を指定する（あれば上書き）
```

手元へファイルを入れる経路は `cdk.py push`（PC から）と `scp`（SSH の相手
から）だけで、Web 上のものを取る道が無かった。http / https だけ、
オプションは URL と名前だけ（人間の指定）。

#### 形は scp と同じ。専用タスクは作らない

| | どうするか |
|---|---|
| 接続（名前解決・TCP・TLS・リダイレクト・ヘッダ） | **待つ**（期限 8 秒）。scp の認証待ちと同じ |
| 本体 | **メインループが `cdk_wget_poll()` で刻む** |
| シェル | 受け取り中は止める (`SESSION_WGET`)。理由は §8.4 と同じ |

`esp_http_client_open` / `fetch_headers` は刻めない（`getaddrinfo` も
TLS ハンドシェイクも途中で戻らない）ので、そこは待つ。**本体を刻めるかが
決め手だった。** IDF v5.5.5 の `esp_http_client_read` は呼ぶたびに
`client->timeout_ms` で select し、来ていなければ `-ESP_ERR_HTTP_EAGAIN`
を返す。`esp_http_client_set_timeout_ms` はフィールドを書き換えるだけで、
次の read から効く。だからヘッダを取ったあとで期限を 10ms に落とす。

**ただし期限がかかるのは transport の read 1 回ごとで、`esp_http_client_read`
1 呼び出しごとではない。** 頼んだ量が埋まるまで受信バッファ（既定 512B）
単位で繰り返すので、4KB を頼むと 1 呼び出しで最大 8 回待つ。止まる長さの
上限は「頼んだ量 ÷ 受信バッファ × 期限」。だから 1 回に頼むのは 512B に
抑えた（受信バッファを広げる手は、esp_http_client が内部 DRAM から取るので
採らない）。最初は 4KB を頼む形で書いていて、レビューで指摘された。

**初期化時の timeout を最初から短くしてはいけない。** 同じ値が接続と
TLS ハンドシェイクにも使われるので、実在のサーバーで繋がらなくなる。

1 周あたり **30ms まで**読む（回数の上限 32 は保険）。**満杯で返らなかったら
その周はやめる。** 汲み切ったあとの読みは必ず期限いっぱい待つ。呼び出しの
途中には割り込めないので、時計は呼び出しの間で見る。

#### 実機で直した 3 つ（2026-09-17）

終了時のログに「周の数 / 回数で切った周 / 時間で切った周 / 最長の周 /
仕上げの時間」を出すようにして、数字を見ながら詰めた。

| | 変える前 | 変えた後 |
|---|---|---|
| 1 周 8 回まで → 30ms まで | 約 80KB/s、周の 7 割が回数切れ | 約 107KB/s、9 割が時間切れ |
| SD へ 512B ずつ書く → 4KB 溜めて書く | 周の 2 割が 30ms の時間切れ | 小さく改善（上と合わせて測定） |
| https のソケットをノンブロッキングに | **最長 200ms**・約 78KB/s | 最長 62ms・約 105KB/s |

3 つ目が一番効いた。**期限は select にしかかからない。** TLS では select が
「読める」と言ったあと、mbedtls がレコード 1 つ分（最大 16KB）揃うまで
ブロッキングの recv で待つ。ヘッダを取ったあとでソケットを O_NONBLOCK に
すると WANT_READ で戻り、transport がそれを期限切れ（`ERR_TCP_TRANSPORT_
CONNECTION_TIMEOUT` = 0）に写すので、`esp_http_client_read` は EAGAIN を
返すだけになる。**代わりにその度に `transport_base` が E、`HTTP_CLIENT` が W を
1 行出す**ので、受け取り中だけこの 2 つのタグを黙らせ、終わったら戻す
（115200bps のログに出すだけで周が延びる）。

**残っている長い周は最後の 1 回だけ。** 書き残し・閉じる・古いファイルの
削除・rename で 97〜152ms（SD の FAT 操作）。scp の FINISH と同じで、
終わりに 1 回だけなので受け入れた。

測り方の注意: `cdk.py ping` の往復は PC 側のプロセス起動が約 450ms を占める。
受け取り中と待機中で同じ値だったので「メインループは止まっていない」とは
言えるが、数十 ms の差はこれでは見えない。周の長さは上のログで見ること。

#### 名前の規則（`cdk_shell_wget_name`、ホストテストあり）

- パスの最後の `/` より後ろ、`?` `#` より前。`%XX` は復号する
- 空（`http://h/` など）は `index.html`（本家 wget と同じ）
- FAT で使えない `\ / : * ? " < > |` と制御文字は `_`。`%2F` を復号して
  できた `/` も `_` で、**階層は作らない**
- **壊れた UTF-8 は 1 バイトずつ `_`。** `CONFIG_FATFS_API_ENCODING_UTF_8`
  なので、壊れた列は `fopen` が通らない
- 先頭の空白と末尾の `.` / 空白は削る。**FATFS が黙って削るので、削る前の
  名前で「既にあるか」を見ると食い違う**
- 長ければ 255 バイト（と呼び側の上限）に、**UTF-8 の文字境界で**、
  拡張子（16 バイトまで）を残して切る

#### 同名の扱い

- 名前を**省いた**とき: 上書きしない。`a.txt.1` … `a.txt.99` に逃がす
  （本家 wget と同じ付け方）。**`.tmp` があるものも同名とみなす**
  （書きかけの隣に置くと、片方の後片付けがもう片方を消す）
- 名前を**指定した**とき: 上書き（scp と同じ）

どちらも `.tmp` に書き上げてから `remove` → `rename`
（FATFS の rename は上書きしない）。失敗・中止では `.tmp` を消す。
**ただし rename で失敗したときは `.tmp` を残す。** 上書きの指定だと元は
もう消してあるので、消すと両方失う（scp の受信と同じ約束）。

#### できないこと

- **長さの分からない応答**（`Content-Length` も chunked も無い、切断で終わる
  応答）。esp_http_client は `data_process < content_length(-1)` で残りを
  判断するので read が即 0 を返す。黙って 0 バイトを置かないよう、ヘッダの
  段で断る
- 接続待ちの間の Ctrl-C（scp と同じ）
- 証明書を確かめない接続（`-k`）、認証、POST、再開

#### 検証

- ホスト: `test_shell` に URL の判定・名前の生成・連番の 3 ケース
- 実機 v1（2026-09-17）で確かめたもの:
  - http（chunked）で `index.html`、同じ URL をもう一度で `index.html.1` / `.2`
  - `http://github.com/…/raw/…` → https → raw.githubusercontent.com の
    多段リダイレクト。11358 バイトが Content-Length と一致
  - `https://httpbin.org/status/404` で `HTTP 404`、`.tmp` が残らない
  - `%E3%81%82:x.txt?q=1` → `あ_x.txt`
  - 名前を指定して既存の `index.html` を上書き（chunked の https）
  - 10MB / 4GB のファイルを途中で `cdk.py key ctrl+c` → `止めました`、
    本体も `.tmp` も残らない。進捗行が撮れる
  - 引数なし・3 個・`ftp://`・`http:///a` を断る
- 確かめていないもの: SSH を開いたまま / 再接続待ちの間の `wget`
  （TLS のメモリ）、rename の失敗、SD の容量切れ、長さの分からない応答

### エディタ (`edit <file>`)

`components/cdk_edit/`。microSD 上のプレーンテキストを SKK 付きで編集する。

**出力は端末へのバイト列**（`cdk_shell` と同じ）。エスケープ列を組んで
`cdk_term` に流すので、描画・フォント・桁計算は検証済みの経路をそのまま通る。
画面を自前でセル単位に描くと、ホストの基準レンダラと比べられなくなる。

本文は**平たいバイト配列 + memmove**。ギャップバッファや piece table は
使わない。128KB の memmove は 1 打鍵あたりの処理として十分に速く、
速さのために正しさを危うくする理由がない。領域は起動時に PSRAM から
1 回だけ確保する（§14）。

**文書の上限は 128KB**（`EDIT_ARENA_BYTES`）。これを超えるファイルは開けない
（読取専用にして理由を出す）。日本語の文章なら 4 万字ぶんなので、この
用途では当たらないはずだが、当たったときに理由が分からないと困るので
ここに書いておく。残りが 1KB を切ったらステータス行で知らせる。

#### 折り返し

日本語の文章を書くので**折り返す**（横スクロールしない）。

**折り返しの判断は `wrap_break()` 1 か所だけ。** 描画・上下移動・
スクロールが同じ判断を通る。ここを 2 か所で計算すると、全角が右端に
来たときにカーソルだけ別の場所へ行く（M1 の枠線・M3 のカーソルずれと
同じ形の不具合）。上下移動を足すときにその誘惑が出る。

行がちょうど右端まで埋まっているとき、カーソルは次の行の頭に出る。
本文の末尾のカーソルも「幅 1 の居場所」として同じ判定を通している。

#### キー

| キー | 動作 |
|---|---|
| `Ctrl-S` | 保存 |
| `Ctrl-Q` | 終了（変更があれば 1 回聞き返す） |
| `Ctrl-A` / `Home` | 表示行の先頭 |
| `Ctrl-E` / `End` | 表示行の末尾 |
| 矢印 / `PgUp` / `PgDn` | 移動 |
| `Ctrl-J` | かな入力（§9） |

**`Ctrl-J` 以外の `Ctrl` 付きは SKK が食べない。** ▽ や ▼ の途中でも
`Ctrl-S` が届く。全部食べると変換中だけキーが効かなくなり、
「壊れている」ようにしか見えない。

日本語入力のモードは**セッションごとに覚える**。1 つにすると、
エディタでかな入力にしたまま抜けたときにシェルのコマンドが変換され、
`ls` が「ｌｓ」になって何も打てなくなる。

#### 壊さないための決まり

- **入りきらないファイルは読み込まない。** 途中まで読んで保存すると、
  その時点でファイルの後半が消える。切り詰めたものを黙って持つのは
  エディタではなくシュレッダー。読取専用にして保存も禁じる。
- **保存は `.tmp` に書いてから `rename`。** 元のファイルに直接書くと、
  途中で電源が落ちたり SD が抜けたりしたときに、書きかけのものが
  元の場所に残る。FATFS の `rename` は上書きしないので先に `remove` する。
- **ステータス行は画面幅で切る。** 右端を超えると端末が改行し、
  画面全体が 1 行スクロールして本文が上へ流れて消える。

#### まだやっていないこと

- **取り消し (undo)。** 1 段でも欲しいが、まずは折り返しとカーソルを
  確かなものにするほうを優先した。
- 検索・置換、範囲選択、コピー＆ペースト
- 行番号の表示、タブ幅の設定（いまタブは空白 4 つで代える）

## 11. ストレージ

| 用途 | 場所 |
|---|---|
| WiFi 認証情報、設定 | NVS |
| SKK 辞書 | フラッシュ `skkdict` (8MB)。SD `/sdcard/skk/SKK-JISYO.bin` があればそちら |
| 個人辞書（学習） | microSD `/sdcard/skk/user.dic` |
| known_hosts、SSH 鍵 | microSD `/sdcard/ssh/` |
| テキストファイル | microSD 任意 |
| フォント | フラッシュ rodata（SD 不要） |

CoreS3 の microSD は LCD と SPI バスを共有する。同一バスの排他制御が要る
（`esp_lcd` の SPI と `sdspi` を同じホストに載せ、トランザクション単位で共存させる）。
**LCD 転送中に SD アクセスが割り込むと画面が壊れる**ので、
キャンバス転送タスクと SD アクセスをミューテックスで直列化する。

さらに CoreS3 では **LCD の DC と SD の MISO が同じ G35**。排他だけでは足りず、
所有者が変わるたびにピンの向きを切り替える必要がある（`port_spibus`）。
LCD 側は出力、SD 側は入力。再帰ミューテックスにしてあるのは、
`cdk_sd_lock()` を持ったまま呼ぶ関数の中でもう一度取ることがあるため。

### FATFS の長いファイル名

**`CONFIG_FATFS_LFN_HEAP=y` が要る。** ESP-IDF の既定は `FATFS_LFN_NONE` で、
8.3 の短縮名しか扱えない。`known_hosts` は 11 文字なので `fopen` が
`FR_INVALID_NAME` で失敗する。

これは原因に辿りつきにくい。libssh2 からは `rc=-16 (LIBSSH2_ERROR_FILE)` としか
見えず、「SD が壊れている」「ディレクトリが無い」と誤診しやすい。
**見分け方は `ls`**: カードの実ファイルが `LICENC~1.BRO` のように
チルダ付きで出ていれば LFN が無効。

`FATFS_LFN_STACK` ではなく HEAP にしているのは、
255 文字 x 2 バイトが各タスクのスタックに乗るのを避けるため。
`CONFIG_FATFS_API_ENCODING_UTF_8=y` も入れて、端末・`cdk_term` と
ファイル名の文字コードを揃えてある（変換点を作らない）。

パーティション（16MB）。`gen_esp32part.py --flash-size 16MB` で検証済み:

```
# Name,   Type, SubType, Offset,  Size
nvs,      data, nvs,     ,        24K     # 0x009000
phy_init, data, phy,     ,        4K      # 0x00f000
factory,  app,  factory, ,        4M      # 0x010000
skkdict,  data, 0x40,    ,        4M      # 0x410000
storage,  data, fat,     ,        4M      # 0x810000
                                          # 0xc10000 以降 約4MB 空き
```

`skkdict` は SD 無しでも SKK が使えるようにするための予備領域。
SD が本命なので、不要なら削って `storage` か OTA に回せる（M5 までに判断すれば良い）。
OTA は当面不要（`factory` 単独）。必要になったら空き 4MB を `ota_1` にする。

## 13. マイルストーン

各マイルストーンの完了条件は「エージェントがコマンド一発で検証できること」。

**次のマイルストーンを始める前に、必ず両方を通すこと。**

```

ホスト側だけなら Claude Code の `Stop` フックで自動化できる（実機が要らず
1 秒で終わる）。実機の `selftest` は機器の状態に依るので手で回す。

#### 入力の流れ

```
制御チャネル KEY  ─────────────────┐
制御チャネル TEXT → cdk_keys_decode ┴→ route_key ─┬→ cdk_shell   (SHELL)
USB HID (M7)      ────────────────────────────────┴→ cdk_keys_encode → SSH
```

**キーの行き先を決めるのは `route_key` だけ。** ここを分散させると
「このキーは誰が受け取るのか」が条件分岐の集合になって追えなくなる。
SSH が切れたときにシェルへ戻す遷移も同じ場所にある。

シェルはキーイベントだけを見る。エスケープ列の解釈は `cdk_keys_decode` が
一手に引き受けるので、シェル側に 2 つ目の VT パーサを持たなくて済む。
USB キーボード（M7）は最初からキーイベントで来るので、この境界がそのまま使える。

#### 認証情報

`set` コマンドで NVS に入れる。起動時は NVS を読み、無ければ `secrets.h`
（`.env` から `tools/gen_secrets.py` が生成、gitignore 済み）で補って
その場で NVS に書く。`secrets.h` は初回の種でしかない。

`set` の表示ではパスワードだけ伏せる（文字数は出す）。SSID やホスト名まで
伏せると設定が合っているか確認できず、かえって危ない。

#### GPIO の安全弁

CoreS3 は空きピンが少ない。LCD / SD / 内蔵 I2C / USB / ログ UART / カメラ /
フラッシュ・PSRAM のピンは `cdk_gpio_is_reserved()` で弾き、**何に使われているかを
名前で返す**。黙って触ると「画面が消える」「書き込めなくなる」といった
原因の分かりにくい壊れ方をするため。

`gpio mode <pin> out` は `GPIO_MODE_INPUT_OUTPUT` にしている。
`GPIO_MODE_OUTPUT` だと入力バッファが切れ、直後の `gpio get` が
設定した値ではなく 0 を返す。

#### 見送ったもの

**`uart monitor` は入れていない** → **入れた（2026-09-12、下の「シリアル端末」）。**
保留の理由は端末を占有してセッションの切り替えと競合することで、
先に決めるべきとしていた 2 点はこう決めた:

- **抜けるキーは `Ctrl-] q` の 2 打鍵。** `route_key` に
  「UART セッション」を足す形は想定どおり。
- **抜けるキー自体は、素の `Ctrl-]` がそのまま 0x1D として相手へ通る。**
  前置キーにしたので、エスケープのための別の綴りを増やさずに済んだ。

`Ctrl-]` 単独ではなく 2 打鍵にしたのは、**バイナリを流す相手に
0x1D を送れなくすると詰む**から。1 打鍵で抜ける方式だと、
「抜けるキーを送るためのエスケープ」をもう 1 つ決める必要があった。

基板の仕様と検証は **HARDWARE_DESIGN.md**（2026-08-28 に検証済み、指摘 12 件は決着）。

#### 基板の切り分け ✅ できている (2026-08-28)

試作機（CoreS3）と最終ハード（v1）で **PSRAM のモードが違う**。
CoreS3 は quad、N16R8 は octal で、間違えると起動時に abort する。
コンソールの出口も違う（CoreS3 は UART1 → FT232、v1 は UART0）。

```
python tools/cdk.py build              # 既定 = cores3
python tools/cdk.py build --board v1
```

| どこ | 何を持つ |
|---|---|
| `sdkconfig.defaults` | 基板に依らない設定だけ |
| `sdkconfig.defaults.cores3` / `.v1` | PSRAM のモード、コンソールの出口、`CONFIG_CDK_BOARD_*` |
| `components_port/port_board/include/cdk_board.h` | ピン番号と「その基板にその機能があるか」 |

**基板を変えるときは `sdkconfig` を作り直す。** ESP-IDF は既存の
`sdkconfig` の値を defaults より優先するので、消さないと前の基板の
PSRAM 設定が残る。`cdk.py build --board` が `.cdk_board` を見て自動で消す。

機能の有無は `CDK_BOARD_HAS_*` で **0/1 を必ず定義する**。`#ifdef` にすると、
綴りを間違えたときに黙って「機能なし」に倒れる。

ポート層で基板ごとに分かれているのは 3 か所だけ:

| ファイル | 違い |
|---|---|
| `port_spibus` | CoreS3 だけ G35 の向きを切り替える。v1 は別バスなのでロックだけ |
| `port_display` | CoreS3 は BSP + エンディアン入れ替え。v1 は ILI9488 を SPI2 で直接 |
| `port_storage` | CoreS3 は BSP。v1 は SPI3 に sdspi を自分で立てる |

**ピン番号は 2 か所（HARDWARE_DESIGN.md と `cdk_board.h`）にある。**
片方だけ直すと、基板は正しいのにファームが別のピンを叩くという、実機でしか
出ないうえに原因の分かりにくい壊れ方をする。`tools/check_board_pins.py` が
ctest（`board_pins`）で両方を突き合わせている。

#### v1 の液晶 — ILI9488

**SPI 接続では 16bit を受け付けない。** 18bit (RGB666) の 3 バイトしか通らない。
転送量は 480x320 の全画面で 450KB（RGB565 なら 300KB）。帯単位で送るので
全画面ぶんを持つ必要はなく、16 行ぶんの変換バッファ 23KB を起動時に
1 回だけ確保する（§14）。

初期化列は `atanisoft/esp_lcd_ili9488` に任せる。ベンダのレジスタ列を
当てずっぽうで書くと、映らないときに「配線」「初期化」「転送」のどれが
悪いのか切り分けられない。

> **ドライバの `draw_bitmap` に境界検査が無い。** `buffer_size`（画素数）を
> 超える画素数を渡すとヒープを壊す。帯の行数 (`BOUNCE_ROWS`) と必ず一致させる。
> 1.0.x は転送のたびに DMA バッファを malloc し、失敗すると**無限ループ**する。
> 1.1.x で起動時に 1 回確保する形に直っているので、そちらを使う。

CoreS3 とは転送前の処理が違うだけで、帯の切り出しとダーティ管理は共通:

| | 変換 | バッファ |
|---|---|---|
| CoreS3 (ILI9342C) | エンディアン入れ替え | 自前のバウンス 2 枚 |
| v1 (ILI9488) | RGB565 → RGB666 | ドライバ内に 1 枚（キャンバスを直接渡す） |

#### 画面が 53x20 から 80x26 に変わる

桁数・行数を持っている側を洗うこと。

- [ ] `cdk_edit_set_size()` は `edit` を開くときにしか呼んでいない。
      画面の大きさが動く可能性が出たら、変わったときに呼び直す口が要る。
- [ ] `cdk_ssh_resize()` は API があるだけで**呼ぶ側がまだ無い**（M2 からの残件）。
- [ ] `banner.vt` の基準画像は 320x240 で作ってある。`selftest` の比較を
      新しい寸法でやり直す。
- [x] ステータス帯 — 作った（下の「ステータス帯」）。**ただし §0 の
      「余りの 8px」ではなく 1 行使う**。理由はそこに書いた。

USB HID のキーは最初から `cdk_key_t` で来るので、`route_key` から下は
そのまま使える（M1 でその境界を作ってある）。**`Ctrl-J` がバイト列経由では
届かない**問題も、HID なら区別できるので M7 で解消する（§9.2）。

## 14. コーディング規約

- C11、`snake_case`、公開シンボルは `cdk_` プレフィクス
- ファイルは UTF-8（BOM なし）、LF
- `components/` では `assert` と戻り値エラーコード。`ESP_LOG` / `ESP_ERROR_CHECK` は禁止
- `components_port/` では `esp_err_t` を返し `ESP_LOGx` を使う
- 動的確保は起動時のみを原則とする。端末バッファ・キャンバス・辞書索引は起動時に確保して以後固定

#### USB キーボード ✅ できている (2026-08-29)

実機の HHKB (VID=04FE PID=000D) で入力できる。`abc`、`@`、`:`、`"` を確認。

```
components/cdk_hid/          ブートプロトコル 8 バイト → キーイベント（純 C）
components_port/port_usbhid/ usb_host + espressif/usb_host_hid、VBUS、キュー
```

**レポートディスクリプタは読まない。** キーボードなら全機種がブート
プロトコル（modifier / 予約 / usage id x6 の 8 バイト固定）を持っていて、
その usage id が `cdk_keycode_t` と**そのまま同じ値**になる。
Enter も矢印も F キーも、変換表を書かずに `keycode` へ入れるだけで済む。

##### キーはメインループだけが組み立てる

USB 側がキューに積むのは**キーではなくレポート**。

```
[USB タスク] レポートをキューへ
                    ↓
[メインループ] cdk_usbhid_poll → cdk_hid_report → route_key
```

`route_key` は端末・画面・SKK・SSH を触るので USB のタスクから呼べない。
キーに変換してから積むこともできるが、そうすると CapsLock の状態と
オートリピートの時計を 2 つのタスクから触ることになる。
**レポートのまま渡せば、状態はぜんぶメインループ側に閉じる。**

##### オートリピートは時計で進める

**ブートキーボードは状態が変わったときしかレポートを送らない。**
押しっぱなしでも何も来ない。だからレポート到着を数えて繰り返すと、
「別のキーを押したときだけ連射される」という妙な動きになる。
`cdk_hid_tick()` にメインループの時刻を渡して進める。

##### 配列は決め打ちできない

同じキーの usage id は配列によらず同じで、**刻印だけが違う**。
`espressif/usb_host_hid` は HID ディスクリプタの `bCountryCode` を
外に出さないので、挿さっているのがどちらかは分からない。

決め手は 1 打鍵で取れる。**`@` がどの usage id から出るか**:

| | usage | 修飾 |
|---|---|---|
| US | 0x1F (2) | Shift |
| JIS | 0x2F (P の右) | なし |

実際 US のまま `@` のキーを打ったら `[` が出た。それで JIS と確定した。
`set keymap us|jis` で切り替わり、NVS に残る。基板の既定は
`CDK_BOARD_KEYMAP_JIS_DEFAULT`（v1 = JIS）。

JIS にしか無い usage (0x87 ろ / 0x89 ￥ など) が来たら警告を出すが、
**勝手には切り替えない**。`set keymap` で明示した設定を裏切らないため。

##### SET_PROTOCOL が通らない個体がある

実機の HHKB は `SET_PROTOCOL(boot)` がタイムアウトする。それでも
8 バイトのブート形式で送ってくるので、**警告だけ出して続行する**。
ここで諦めると「制御転送だけ通らないキーボード」が全部使えなくなる。
長さが 8 未満のレポートは捨てているので、形式が違えばそこで落ちる。

#### 文字の 2 倍表示 ✅ できている (2026-08-29)

展示など離れて見る用。`set fontscale 2` → 再起動で **40桁 x 13行**。

```
等倍  480/6  = 80桁   320/12 = 26行   (312px + 余り 8px)
2倍   480/12 = 40桁   320/24 = 13行   (312px + 余り 8px)
```

**どちらも余りがちょうど 8px** で、§0 がステータス帯に予約している分と一致する。

##### フォントは差し替えず、画素ごと広げる

24px の日本語ビットマップフォントを別に持つと、**字形もカバー範囲も変わって
「その字だけ出ない」問題を新しく作る**。等倍のグリフを 2x2 に広げるだけなら、
字形もカバー範囲もそのままで容量も増えない。

間は補間しない。ビットマップフォントは字形そのものが最終形なので、
なめらかにすると輪郭が濁ってかえって読みにくい。

倍率は `cdk_screen_t` に 1 つ持つだけ。カーソルも未確定文字列も全角も
エディタも**同じ `cdk_screen_draw_cell` を通っている**ので、そこだけで全部に効く。
下線と取り消し線は倍率ぶん太らせる（1 画素のままだと線だけ細く浮く）。

##### 再起動が要る

桁数と行数が変わるので `cdk_term` を作り直す必要がある。ガンマや keymap と
違ってその場では反映できない。`set fontscale` は**再起動が要ることを言う**
（黙って効かないほうが悪い）。

副次的に、SSH の PTY は接続時に寸法が決まるので、再起動を挟めば正しい大きさで
繋がる。M2 から開いたままの `cdk_ssh_resize()` を実装せずに済んでいる。

##### 基準レンダラにも倍率を渡す

ガンマと同じ。`SHOT_INFO` に載せて `cdk_render --scale=` へ流す。
これが無いと 2 倍にした瞬間に `shot --verify` が落ち、**しかも落ちる理由が
倍率違いなので「実機が壊れた」ように見える**。2 倍でも完全一致を確認済み。

#### ステータス帯 ✅ できている (2026-08-29)

`set statusbar on` → 再起動で最下段に出る。**本文が 1 行減る**ので既定は off。

```
192.168.1.97 あ SD14G KBD
```

出すもの: IP / SSH / かな入力の状態 / SD / USB キーボード / 電池。
入りきらない項目は**後ろから丸ごと落とす**（途中でちょん切ると
`192.168.1.9` が別のアドレスに見える）。桁数は `cdk_char_width` で数える。
バイト数で数えると日本語が入った瞬間にずれる（#21 と同じ壊れ方）。

##### §0 からの逸脱: 8px ではなく 1 行使う

§0 は「26行 = 312px、余り 8px を帯に使う」と書いてあるが、そうしなかった。

- **8px に 12px のフォントは入らない。**
- 専用の小さいフォント（4x6 など）を作る手はあるが、**2 倍表示のときに
  帯だけ極小のまま**になり、展示で遠くから読めない。
- 1 行使えば拡大率にそのまま追随する（等倍 12px / 2倍 24px）。

代償は本文が 1 行減ること（80x26 → 80x25、40x13 → 40x12）。
「26行は仕方ない」で受け入れてもらった経緯があるので**既定は off**にした。

##### DECSTBM で最下行を確保する手は使えない

スクロール領域を `ESC[1;25r` にして最下行を守る方法は、**SSH 先の
プログラムに壊される**。`vi` も `less` も `top` も自分でスクロール領域を
設定するか `ESC[r` で解除して全画面を使う。SSH してそれらを動かすのが
この機械の主目的なので、これは例外ではなく通常動作。

**帯は端末グリッドの外に置き、端末には 1 行少なく渡す。** エスケープを
一切使わないので遠隔のプログラムから触れない。ついでに #29（ステータス行が
幅を超えて画面全体がスクロールし本文が消える）の経路も構造的に消える。

##### 検証は本文だけを比べる

帯の中身（IP・電池）はホスト側で再現できない。そこで `SHOT_INFO` に
帯の高さを載せ、`shot --verify` は**本文の範囲だけ**を比べる。

**「検証中は帯を描かない」という分岐は入れなかった。** それは検証されて
いるときだけ挙動が違う装置になり、#26（selftest が M2 から壊れていた）と
同じ穴になる。比較の性質を変えるほうが、装置に分岐を足すより安全。

`cdk_render` にも `--status-h` を渡す。実機は帯のぶん 1 行少ない端末を
作っているので、基準側が 1 行多いと折り返しとスクロールがずれ、
本文だけを比べても食い違う。

##### 電池は電圧だけ出す (2026-09-17)

GPIO5 (ADC1_CH4) には電池電圧の **1/2** が来る（`CDK_BOARD_BATT_DIV`）。
`cdk_batt_read_mv` が校正済みの値を 8 回平均して 2 倍する。帯と `info` に出す。

- **残量 % にはしない。** NiMH とアルカリのどちらも入るので、
  電圧と残量の対応が 1 本に決まらない。電圧そのものなら嘘にならない。
- **帯のためには 10 秒に 1 回しか読まない。** メインループは速く回るので
  毎周読むと無駄だし、数 mV の揺れで帯の描き直しが止まらなくなる。
  `info` はその場で読む。
- 校正（curve fitting）が使えないときは出さない。生値から換算した電圧は
  信用できないので、0 を渡して帯から消す。
- 実機（NiMH x2）で `adc read 4` = 1348 mV に対し、`info` / 帯とも 2.67V。

#### 公開鍵認証 ✅ 実装 (2026-08-29)

```
ssh keygen     ECDSA P-256 を実機で作り、公開鍵 1 行を出す
ssh key        いまの鍵の指紋と公開鍵を出す
ssh            公開鍵 → パスワード の順で試す
```

**公開鍵を先に試す。** 逆にすると、鍵を置いたのに黙ってパスワードで入って
いた、という状態に気づけない。失敗しても諦めずパスワードへ落ちる
（鍵が authorized_keys に無いのは普通に起きる）。

##### 鍵は実機で作る

SD へファイルを送り込む口が無いので、他に鍵を持ち込む手段がない。
実機で作れば、出てきた公開鍵をサーバーへ貼るだけで済む。

**上書きは黙ってやらない**（`ssh keygen -f` が要る）。鍵を消すと入れなくなる。
FAT に権限は無いので、**カードを抜けば秘密鍵は読める**。そう表示している。

##### mbedTLS バックエンドの制約を 2 つ踏んだ

| | |
|---|---|
| **ed25519 は使えない** | `LIBSSH2_ED25519 = 0`。`ssh-keygen` の既定なので必ず踏む。RSA と ECDSA のみ |
| **秘密鍵からの公開鍵導出は RSA 専用** | `_libssh2_mbedtls_pub_priv_key` が `MBEDTLS_PK_RSA` 以外を弾く |

2 つ目のせいで、`libssh2_userauth_publickey_fromfile_ex` に公開鍵 NULL を
渡すと ECDSA の鍵が `rc=-16 (Key type not supported)` で落ちる。
**これは「鍵が未登録」と区別がつかない**ので、原因の分からない失敗になる。

ECDSA の署名と秘密鍵の読み込み自体は実装されているので、**`.pub` を明示的に
渡せば通る**。`.pub` を渡したら `rc=-18 (Username/PublicKey combination
invalid)` に変わった。これは「鍵は正しく提示できたがサーバーに登録が無い」で、
こちら側でできる確認の限界。

##### 検証: 別実装と突き合わせた

実機が作った公開鍵をログに出し（**公開鍵は公開してよい。秘密鍵は絶対に
出さない**）、`ssh-keygen -l -f` に食わせた。

```
実機          : SHA256:EdkLEb+mPmDNjBfDGEJepj/qLS332bvGM0UfRA/ZLAc
ssh-keygen -l : 256 SHA256:EdkLEb+mPmDNjBfDGEJepj/qLS332bvGM0UfRA/ZLAc (ECDSA)
```

符号化・base64・指紋の計算が OpenSSH と一致している。
`cdk_sshkey` のホストテストも、ssh-keygen が作った本物の鍵を期待値にしている
（自分で組んだ期待値だと、同じ間違いをしていれば通ってしまう。#7 の形）。

#### 再接続 ✅ できている (2026-08-29)

通信が切れたら 1 → 2 → 4 → 8 → 15 秒…と待って繋ぎ直す（最大 8 回）。
`set ssh.recon off` で止められる。

##### 繋ぎ直してよい切れ方だけ繋ぎ直す

| 切れ方 | どうするか |
|---|---|
| `CDK_SSH_DISCONNECT_ERROR` 通信断 | **繋ぎ直す** |
| `CDK_SSH_DISCONNECT_EOF` リモートが閉じた (`exit`) | 繋ぎ直さない |
| `CDK_SSH_DISCONNECT_LOCAL` `ssh close` | 繋ぎ直さない |

**`exit` で繋ぎ直すと抜ける手段が無くなる。** ここを一緒くたにすると、
使う人から見て「SSH から出られない機械」になる。read/write のエラー経路と
`libssh2_channel_eof()` の経路はもともと別なので、理由を持たせるだけで分かれる。

##### 待っている間もシェルは使える

再接続は画面を占有しない。待っている間に `set` を直したり `ssh close` したり
できる。**どのキーでも中止する** — 特定のキーにすると、それを覚えていない人は
止められない。展示中に勝手に繋ぎ直し続けるのを止められないのは困る。

##### バックオフは純 C（`cdk_retry`）

時刻は呼び出し側が渡す。ホストテストで固定したのは主にこの 2 つ:

- **時刻が一周しても止まる/止まらないが正しいこと。** 符号なしで比べると
  49 日で一周した瞬間に「まだ来ていない」と判断して永久に繋ぎ直さなくなる。
  SSH は繋ぎっぱなしにするので実際にまたぐ。
- **上限で頭打ちにしてから倍にすること。** 先に倍にすると 32bit を溢れて
  待ちが短くなり、上限を上げたつもりが逆に連打になる。

上限自体も 2^31 ms で頭打ちにしている。一周をまたぐ判定を符号付きの差で
やっている以上、それより長い間隔は表現できない（テストで固定した）。

##### 検証

通信断は意図的に起こせないので、**`EOF` を一時的に `ERROR` として扱う
故障注入**で経路を通した。ログに切断 → 1 秒待ち → 再接続 → 接続完了が並ぶ。
戻したあとで `exit` が繋ぎ直さないことも確認した。

> **中止（キー入力で止める）は実機で通していない。** 相手が生きていると
> 1 回目で繋がってしまい、止める隙が無い。状態機械はホストテストで
> 見ているが、結線は目視のみ。

ファームを焼き直さずに機能を足せるようにする。`.wasm` を microSD に置いて
`wasm run` で走らせる。

```
$ wasm run apps/hello.wasm foo
こんにちは、wasm から
端末は 40桁 x 12行
引数[0] = apps/hello.wasm
引数[1] = foo
wasm  : 終了 (0)
```

### 15.1 なぜ独自 ABI にしたか

WASI でも POSIX 互換でもない。理由は 3 つ:

- WASI を名乗ると `fd_prestat_dir_name` や `clock_res_get` まで期待される。
  **実装しない関数が「壊れている関数」になる。** 名乗らなければ「無い」で済む。
- POSIX 互換は errno・シグナル・ブロッキングの意味論を全部背負う。
  この機械はメインループ 1 本で回っていて、その意味論は載らない。
- 独自なら**引数を i32 と (ptr,len) の隣接ペアだけ**に揃えられる。
  そこまで揃えると、サンドボックスの境界検査が機械的に検査できる形になる。

### 15.2 ランタイムは wasm3

| | wasm3 | WAMR |
|---|---|---|
| ライセンス | MIT | Apache 2.0 |
| 中身 | 純 C99 の 12 ファイル | ビルドシステムごと大きい |
| ESP-IDF | 自分でベンダリング | 公式コンポーネントあり |
| AOT / JIT | 無い | ある |
| **ホストビルドへの取り込み** | **そのまま通る** | 手間がかかる |

最後の 1 行で決めた。§13 の「失敗したまま誰も見ていない検証は、無いのと
同じ」への対策として、**ctest が本物の `.wasm` を実機と同じコードで回せる**
ことの価値が AOT より大きい。実際 clang で 12 ファイルとも無警告で通った。

上流: `components_port/wasm3/upstream/`（コミットは `COMMIT.txt`）。
差分は当てていない（`PATCHES.md`）。

### 15.3 層

§1 の境界をそのまま延長する。**wasm3 のヘッダを純 C コアに入れない。**

```
components/cdk_wasm/          純 C。ABI・fd 表・パスのサンドボックス・リング
components_port/wasm3/        上流のベンダリング（libssh2 と同じ作法）
components_port/port_wasm/    wasm3 の出し入れと実機バックエンド
main/cdk_wasmcmds.c           wasm コマンド
main/cdk_pushfile.c           cdk.py push の受け側
wasm-sdk/ wasm-apps/          ゲスト側の SDK とサンプル
tools/wasmcc.py               clang のラッパ
```

`port_wasm/` の中は **ESP-IDF に触るかどうか**で割ってある:

| ファイル | IDF | ホストビルド |
|---|---|---|
| `port_wasm_natives.c` | 無し | **入れる**（境界検査がここにある） |
| `port_wasm_vm.c` | 無し | **入れる**（VM の出し入れ） |
| `port_wasm.c` | あり | 入れない（タスク・PSRAM） |
| `port_wasm_backend.c` | あり | 入れない（周辺・SD・ネット） |

ホストビルドが `components_port/` を取り込むのは**ここだけ**。
例外にした理由は「実機と同じ境界検査コードを ctest で回すため」で、
`host/CMakeLists.txt` にも書いてある。

### 15.4 実行モデル — 前面 1 本・専用タスク

**アプリはメインループで走らせない。** この機械はコマンドを
`cdk_shell_key → route_key →` メインループの中で同期実行するので、
そこで回すと画面もキーも制御チャネルも止まり、Ctrl-C すら届かない。

```
wasm run apps/hello.wasm
  → cmd_wasm: PSRAM へ読む → cdk_wasm_run_start → 即 return
  → enter_wasm(): cdk_shell_end(); s_session = SESSION_WASM

[wasm タスク]                   [メインループ]
  m3_CallV(cdk_main)              route_key: キー → cdk_keys_encode → 入力リング
    con_write → 出力リング          出力リングを排出 → cdk_term
    con_read  ← 入力リング          s_dirty なら描画 + フラッシュ
    fs_* / gpio_* / sock_*          終了フラグを見たら enter_shell()
```

**走っている間シェルは止まっている**（`edit` / `ssh` と同じ）。おかげで、
ロックを持たない `port_periph` / `port_cfg` をシェルとアプリが同時に叩く
事故が構造的に起きない。バックグラウンド実行を選ばなかった理由がここ。

端末・画面・SKK を触るのはメインループだけ、という M1 からの不変条件も
壊していない。wasm タスクが触るのはリングとバックエンドだけ。
SD は `cdk_sd_lock` が再帰ミューテックスなので別タスクからでも安全。

リングは**単一生産者・単一消費者**で volatile な head/tail しか持たない。
それで足りるように **wasm タスクをメインタスクと同じ CPU0 に固定**してある。

### 15.5 中断 — Ctrl-C

`route_key` が `SESSION_WASM` のとき Ctrl-C を横取りして停止要求を立てる。
wasm3 には WAMR の `wasm_runtime_terminate` に当たるものが無いので:

- **すべての native の入口で停止要求を見て、立っていたらトラップする。**
  トラップはインタプリタを巻き戻して `m3_CallV` から帰る。
- `sys_delay` は 20ms 刻み、`sock_connect` は 100ms 刻み、
  `sock_recv` は 200ms 上限、`uart_read` は待たない。
  **いちばん詰まりやすい API がいちばん止まらない API にならないこと。**

> **native を一度も呼ばない無限ループは止められない。**
> wasm3 の構造上の限界。`reboot` するしかない。§12 の表に足した。

`wasm stop` は**置いていない**。走っている間はシェルが止まっているので、
そのコマンドに入る道が無い。止める手段は Ctrl-C だけ。

### 15.6 メモリ（実測 2026-08-30）

| もの | 大きさ | どこ |
|---|---|---|
| `.wasm` の置き場 | 256KB (`CDK_WASM_MODULE_MAX`) | PSRAM・起動時に 1 回 |
| wasm タスクのスタック | 64KB (`CDK_WASM_TASK_STACK`) | **PSRAM** |
| `d_m3MaxNativeStack` | 48KB | 上のスタックより小さく |
| wasm3 オペランドスタック | 16KB | wasm3 が確保 |
| ゲストの線形メモリ | 1MB まで（`d_m3MaxLinearMemoryPages=16` で**強制**） | wasm3 が確保 |
| 出力リング / 入力リング | 4KB / 512B | `cdk_wasm` の static |

app は 1,406KB → **1,527KB**（wasm3 + cdk_wasm + port_wasm で +121KB）。

**タスクスタックを内部 DRAM から取れなかった。** 空きは 77,959 バイト
あるのに**最大ブロックが 31,744 バイト**しかなく、32KB の連続領域が
取れずに `wasm run` が「タスクを作れません」で落ちた。内部 DRAM は
この機械でいちばん足りない資源なので、削るのではなくキャンバス・辞書・
エディタ領域と同じく PSRAM へ置いた（`xTaskCreatePinnedToCoreWithCaps`。
消すときは `vTaskDeleteWithCaps`）。

**結果的にそれが正解で、hello.wasm ですら 42KB 使っていた**（高水位は
64KB 中 23,524 バイト残り）。32KB のままだったら、仮に確保できていても
スタックを踏み抜いていた。

> PSRAM スタックのタスクは**フラッシュのキャッシュが無効な間は走れない。**
> wasm タスクが触るのは SD (SPI) と GPIO だけで、NVS への書き込みは
> シェル側でしか起きないので条件を満たしている。ここは増やすときに要注意。

**アリーナ化のパッチは要らなかった。** `d_m3FixedHeap` は static 配列 +
リセットできない bump アロケータで、`wasm run` のたびに食い潰す。素の
`calloc`/`free` のままにして hello.wasm を 10 回走らせたところ、前後の
`free` がバイト単位で一致した（internal 77,959 / 最大 31,744、
spiram 7,561,620 / 最大 7,471,104）。wasm3 は `m3_FreeRuntime` で全部返す。

### 15.7 ABI

インポートモジュール名 `"cdk"`、エントリは `cdk_main` を `(i32 argc) -> i32`。
定義は `components/cdk_wasm/include/cdk_wasm_abi.h`、ゲスト側は
`wasm-sdk/include/cdk_app.h`。**この 2 つは対で直すこと。**

| 群 | 関数 |
|---|---|
| sys | `sys_exit` `sys_now_ms` `sys_delay` `sys_argc` `sys_arg` `sys_random` |
| con | `con_write` `con_read` `con_size` |
| fs | `fs_open` `fs_read` `fs_write` `fs_seek` `fs_close` `fs_size` `fs_unlink` `fs_mkdir` `fs_opendir` `fs_readdir` `fs_closedir` |
| gpio | `gpio_mode` `gpio_set` `gpio_get` `adc_read` |
| i2c | `i2c_open` `i2c_probe` `i2c_write` `i2c_read` `i2c_wrrd` `i2c_close` — **走査は `i2c_probe` で書く。**読みで走査すると相手を止める（§12 の 17） |
| uart | `uart_open` `uart_write` `uart_read` `uart_close` |
| net | `net_up` `sock_open` `sock_connect` `sock_send` `sock_recv` `sock_close` — TLS も同じ 6 本で扱う（下記） |
| gfx | `gfx_size` `gfx_clear` `gfx_fill_rect` `gfx_blit` `gfx_text` `gfx_present` — **予約。`CDK_E_NOSYS` を返す** |

エラーは負の戻り値（`CDK_E_INVAL` -1 / `PERM` -2 / `NOENT` -3 / `IO` -4 /
`NOMEM` -5 / `AGAIN` -6 / `NOSYS` -7 / `TIME` -8 / `ABORT` -9）。

**キー入力は既存の `cdk_keys_encode` を通したバイト列**として `con_read` に
流す。ゲストからは普通の端末に見える。新しいキーの表現を作らない。

#### TLS (2026-09-01)

**TLS は自前で持たず ESP-IDF (esp-tls + 証明書バンドル) に任せる。**
wasm 側に TLS を積む道は、1MB のリニアメモリにも 256KB のモジュール枠にも
入らない。ホストには mbedtls が既に居る（SSH が使っている）。

**インポートは 1 本も増やしていない。** `sock_open` の型を足しただけ:

| 型 | 値 | 意味 |
|---|---|---|
| `CDK_SOCK_TCP` | 0 | 素の TCP |
| `CDK_SOCK_UDP` | 1 | 素の UDP |
| `CDK_SOCK_TLS` | 2 | TLS。証明書バンドルで検証する |
| `CDK_SOCK_TLS_INSECURE` | 3 | TLS。**検証しない** |

開いたあとの `sock_connect` / `sock_send` / `sock_recv` / `sock_close` は
素の TCP とまったく同じ約束で動く（`sock_recv` は 200ms 待って何も無ければ
0、相手が閉じたら `CDK_E_IO`）。`sock_connect` がホスト名を持っているので、
SNI と証明書の照合にそれをそのまま使える。

名前が増えないので `abi_names_match` の `MIN_NAMES` も既存の `.wasm` も
触らずに済む。**ABI を増やさずに機能を足せたのは、ハンドルがスロット番号で
あって fd ではなかったおかげ**（§15.8）。ホストが返す「fd に見える整数」を
`cdk_wasm` は素通しするだけなので、TLS の実体は `port_sock.c` に閉じた。

**同時 2 本まで。ここは実機で決めた。** mbedtls のセッションは
in 16KB + out 4KB を持つ。既定の `CONFIG_MBEDTLS_INTERNAL_MEM_ALLOC` の
ままだとこれが内部 DRAM から取られ、この基板は空きが 75KB あっても連続では
31,744 バイトしか取れない（§15.6）ので、2 本目で破綻した:

```
E esp-aes: Failed to allocate memory
E esp-tls-mbedtls: mbedtls_ssl_handshake returned -0x0001
E esp-tls-mbedtls: write error :-0x0001
```

**壊れるのは 2 本目だけではなかった。** 内部 DRAM が枯れると、既に繋がって
いる 1 本目の read / write も esp-aes の確保に失敗して落ちる。4 本試したときは
`rst:0xc` で再起動した（バックトレースは CORRUPTED）。「新しい接続が開けない」
なら呼び出し側で対処できるが、「動いている接続が巻き添えで壊れる」は対処の
しようがない。

効いたのは **`CONFIG_MBEDTLS_EXTERNAL_MEM_ALLOC=y`**（`sdkconfig.defaults`）。
esp-aes の DMA 記述子は `MALLOC_CAP_DMA` なので**必ず内部 DRAM から取る**
（`esp_aes_dma_core.c`）。小さな確保なのに失敗していたのは、mbedtls の
16KB/4KB が内部を埋めていたから。mbedtls 本体を PSRAM へ追い出して内部を
空けると、2 本ともハンドシェイクから送受信まで通る。

数字: ハンドシェイクは 1 本で 1,917ms、2 本並行でも 1,880〜1,911ms、
4 本並行でも 1,871〜1,920ms。**ほぼ変わらない**＝この時間は網の往復と
証明書の検証が支配していて、mbedtls のバッファがどの RAM にあるかは効かない。
内部 DRAM は TLS を使っても最大ブロック 31,744 のまま動かない。

上限を増やすときは**必ず実機で、SSH を挟んで繰り返し**試すこと。
一度は内部 DRAM のままでも 2 本通ってしまった。**たまたま通る数を上限に
してはいけない。** 4 本も一度は通ったが、2 本ほど繰り返し確かめていないので
上限は 2 にしてある。

`sdkconfig.defaults` に足したのは上の `MBEDTLS_EXTERNAL_MEM_ALLOC` と、
もう 1 組ある。`CDK_SOCK_TLS_INSECURE` のために
`CONFIG_ESP_TLS_INSECURE=y` と `CONFIG_ESP_TLS_SKIP_SERVER_CERT_VERIFY=y` を
入れた。**プロジェクト全体の既定を変えるフラグ**なので理由を書いておく:
esp-tls は CA を一切指定しない cfg を渡されると、検証を飛ばすのではなく
setup ごと失敗する（`esp_tls_mbedtls.c`）。`skip_common_name` はホスト名の
照合と SNI を止めるだけで連鎖の検証は止めない。効くのは「CA を何も指定
しなかったとき」だけで、`CDK_SOCK_TLS` は常に `crt_bundle_attach` を渡すため
この既定には落ちない。SSH は libssh2 が mbedtls を直接叩く経路で esp-tls を
通らない（実機で SSH ログインまで確認した）。

### 15.8 サンドボックス

1. **メモリ。** wasm3 の `m3ApiGetArgMem` は境界検査をしない。
   ポインタ引数はすべて `m3ApiCheckMem` と対にする。
   `m3ApiCheckMem` は長さを uint64 に広げて比べるので、
   **i32 で渡ってくる負の長さも巨大な長さとして弾かれる**（fixture で確認）。

   > 対になっているかは ctest **`wasm_natives_checked`** が見る。
   > 数えるのは「近くにあるか」ではなく **関数ごとの個数の一致**。
   > 前者だと `i2c_wrrd`（バッファ 2 本）や `sock_connect` や `con_size` で
   > 片方だけ検査していても素通りする。1 個消して落ちることを確かめてある。

2. **パス。** `..` を**畳んでから** `/sdcard` の下かを見る
   （`cdk_wasm_path_resolve`、純 C・ホストでテスト）。文字列の先頭だけ
   見る実装だと `/sdcard/../etc` が通る。`/sdcardX` にも騙されない。
   `cdk.py push` の書き込み先も同じ関数を通す。**規則を 2 か所に持たない。**

3. **ピン。** `cdk_gpio_is_reserved` を GPIO・I2C・UART の全部で通す。

4. **ABI の名前。** インポート名の一覧はファームの表・C の SDK・
   Rust の SDK の 3 か所にある。ctest `abi_names_match` が一致を見る
   （§15.14）。

5. **ハンドル。** ファイル 4 / ディレクトリ 2 / ソケット 4 / UART 1 / I2C 1。
   ゲストが見るのは表の添字だけで、`FILE*` も socket fd も渡らない。
   閉じ忘れは `cdk_wasm_ctx_cleanup` が終了時に全部返す。
   ファイルが 4 なのは FATFS の `max_files = 5` のうち 1 本を本体に残すため。

### 15.9 出力は捨てずに待つ

`con_write` はリングが埋まったら**待つ**。捨てる実装にすると、リング 4KB に
対しメインループが 1 周で汲むのは 2KB なので、ファイルを読んで出し続ける
アプリの出力が**画面から静かに消えてログにしか残らない**。端末が本来やるのは
流量制御のほうで、アプリを少し待たせるのが正しい。待つ間も Ctrl-C は効く。

`flood.wasm`（200 行を一息に出す）で 1 つも欠けないことを実機で確認した。

### 15.10 ゲスト側

**WASI SDK は要らない。** clang の wasm32 バックエンドをそのまま使う。

```
python tools/wasmcc.py wasm-apps/hello.c        # → wasm-apps/build/hello.wasm
python tools/wasmcc.py --all
```

自由形式 (`-nostdlib`) なので libc が無い。`memcpy` / `memset` などは
`wasm-sdk/src/cdk_app.c` が自前で持つ。**使っていなくても要る**（clang が
構造体のコピーや配列の初期化で勝手に呼ぶ）。`cdk_printf` は
`%d %u %x %c %s %%` だけ。確保は解放しないバンプ (`cdk_alloc`)。

同じ ABI の Rust 版が `wasm-sdk/rust/` にある（§15.14）。
**当ててみたらファーム側も 2 か所直すことになった**ので、
「変更なしでできる」とは言えなかった。

### 15.11 転送 (`cdk.py push`)

```
python tools/cdk.py push wasm-apps/build/hello.wasm apps/hello.wasm
```

`cdk_proto` に `FILE_BEGIN` / `DATA` / `END` / `OK` を足した。**SD を
抜き差しせずにアプリを更新できることが、エージェントが自分で書いて自分で
試すループの前提。**

フレームごとの CRC は transport の壊れしか見ない。**フレームがまるごと
落ちたことは見つけられない**ので、長さと全体の CRC を `END` で突き合わせる。

### 15.12 実機で見つかったこと

#### 予約ピンの表が試作機のものしか無かった

I2C と UART がピンを取るので予約表を通したところ、この表が CoreS3 の
ピンしか知らないことが分かった。v1 はピン配置がまったく違う。

| | 素通しだったもの | 逆に塞いでいたもの |
|---|---|---|
| v1 | LCD (G8-G14) / SD (G39-G42) / 制御チャネル (G15,G16) / ログ UART (G43,G44) | Grove の I2C (G17,G18) |

**v1 では `gpio set 12` で画面が死に、`gpio set 15` で PC と話せなくなる**
状態だった。`gpio` コマンドからも届く既存の穴で、ユーザーアプリで広がった。
逆に、自分の基板の Grove コネクタに I2C で繋げなかった。

ピン番号の出どころを `cdk_board.h` ひとつにして、表を基板ごとに分けた。

#### あとから見つかった 2 件は §15.14 にある

Rust の SDK を足したときに、**ファーム側の不具合が 2 つ出た**。
どちらも M8 の時点では踏めなかったもの:

- ゲストが線形メモリを大きく宣言すると**ファームが二重解放で落ちる**
- `cdk.py push` が**複数フレームの転送で壊れる**（C のアプリは
  どれも 1 フレームに収まっていたので通っていなかった）

#### 生成した C のエスケープが ESC 実体に潰れた

DEV_STATS の #13 / #14 と同じ。**シェルのヒアドキュメント経由で
エスケープを含む C を書かない。** 今回は `main.c` の 4 か所が壊れた。

### 15.14 Rust の SDK (2026-08-30)

§15.10 に「同じ ABI に Rust から当てるのはファーム側の変更なしでできる」と
書いたが、**実際に当ててみたら 2 か所ファームを直すことになった**（下記）。
書けると言い切ったまま試していなかったぶんが出た形。

置き場は `wasm-sdk/rust/`。`no_std` + `alloc` のクレート `cdk-app` と、
サンプル 10 本。エディションは 2024。

```
python tools/wasmrs.py --all
python tools/cdk.py push wasm-apps/build/rs_hello.wasm apps/rs_hello.wasm
```

**要るのは `rustup target add wasm32-unknown-unknown` だけ。**
C 版が WASI SDK を要らないのと同じで、こちらも wasm-pack などは要らない。

#### 何のために足したか

同じ ABI なのでできることは変わらない。変わるのは**落ち方**:

```
panic: index out of bounds: the len is 3 but the index is 7 (apps\boom\src\lib.rs:21)
wasm  : 落ちました: [trap] unreachable
```

C 版は境界を踏むと `落ちました: out of bounds memory access` としか出ず、
アプリのどこが悪いのかは画面から辿れない。`no_std` なら
`#[panic_handler]` を自分で持てるので、`file:line` を出してからトラップできる。

そのほか `Result` と `?` で戻り値の取りこぼしが減ること、`format!` が
使えること（C 版の SDK には `snprintf` すら無く、`httpget.c` は
リクエスト行を 1 バイトずつ組み立てている）。

#### 層

C 版と同じで、**ABI を知っているのは 1 ファイルだけ**（`cdk-app/src/sys.rs`）。
その上に `Result` と RAII の付いた層を載せる。

インポート名の一覧が **3 か所**になったので、ctest `abi_names_match` で
一致を見る。片方だけに足すと**その言語のアプリだけが動かなくなる**という、
実機でしか出ないうえに原因の切り分けにくい壊れ方をする。

> **空集合どうしで一致しないようにしてある。** 突き合わせる前に 3 か所
> それぞれで 45 個以上あることを確かめる。`wasm_natives_checked` が
> 「0 個 対 0 個」で通っていた前例があるため。名前を 1 個消したときと、
> 正規表現を壊して 0 件にしたときの両方で落ちることを確認済み。

#### 大きさ

| | ファイル | 線形メモリ |
|---|---|---|
| `rs_hello.wasm` | 7,484 バイト | 初期 1 / 最大 16 ページ |
| `rs_du.wasm`（最大） | 18,945 バイト | 同上 |
| 上限 | 262,144 | 16 ページ |

`opt-level="z"` / `lto` / `codegen-units=1` / `panic="abort"` / `strip` を
`Cargo.toml` に固定してある。`format!` の機構を積んで 7.5KB なので余裕がある。

> **1MB という数は 4 か所にある。** 増やすときは全部直すこと。
> `components_port/wasm3/CMakeLists.txt` と `host/CMakeLists.txt`
> （`d_m3MaxLinearMemoryPages=16`、実機とホストで同じ値にする）、
> `wasm-sdk/rust/.cargo/config.toml`（`--max-memory=1048576`）、
> `tools/wasminfo.py`（`MAX_MEMORY_PAGES`）。
> ピン番号や ABI の名前と同じ「複数箇所にある数」だが、いまは
> 機械で突き合わせていない。`abi_names_match` を広げるならここが次の候補。

**`--max-memory=1048576` を rustflags で明示している。** Rust の cdylib は
指定しないと最大を「無制限」として出し、**ロードは通るのに走らせてから
`memory.grow` で落ちる**という分かりにくい形になる。

#### Rust だけが踏む落とし穴

アロケータはバンプで**解放しない**（C 版の `cdk_alloc` と同じ）。線形メモリは
1MB なので、**確保を繰り返すループはいつか必ず落ちる**。実機で測ったところ、
70 バイトの `format!` を回すループは **約 15,000 回**で尽きた
（`memory allocation of 70 bytes failed`）。

同じループを C で書くと確保が起きないので、**ここだけ Rust の挙動が違う。**
`println!` は `core::fmt` が直接書くので確保しない。取扱説明書にも書いた。

#### エディション 2024 で変わるところ

| | 2021 | 2024 |
|---|---|---|
| インポートの宣言 | `extern "C"` | `unsafe extern "C"` |
| エクスポート | `#[no_mangle]` | `#[unsafe(no_mangle)]` |
| `static mut` への参照 | 警告 | **エラー** |

3 つめがアロケータに効く。C 版の `static cdk_size_t s_bump;` は移せないので、
バンプの位置は `AtomicUsize` で持つ（スレッドは無いので排他の意味は無く、
`static mut` を避けるためだけ）。

#### 実機で見つかったこと

##### ゲストの持ち込むファイルでファームが落ちていた

線形メモリを 2MB 宣言する fixture (`f_bigmem`) を足したら **segfault した。**

上流の `m3_LoadModule` は**失敗してもモジュールをランタイムの一覧に繋ぐ**
（途中まで進んだ初期化が他のモジュールの表に関数を書いているかもしれず、
それを宙ぶらりんにしないため。上流のコメントに明記されている）。そこで
`port_wasm_vm.c` が自分から `m3_FreeModule` を呼んでいたので、あとの
`m3_FreeRuntime` と合わせて二重解放になっていた。

**M8 のテストでは踏めなかった。** `f_noentry` は load が成功したあとで
落ち、ゴミバイト列は `m3_ParseModule` の段で弾かれる。`m3_LoadModule` の
**中で**失敗する fixture が今回初めてできた。

ゲストが持ち込むファイルでファームが落ちるので、この機能でいちばん
踏ませたくない類だった。修正は「何もせず `m3_FreeRuntime` に任せる」。

##### `cdk.py push` が複数フレームで壊れていた

Rust のアプリ（5〜19KB）を送ったら 10 本中 6 本が失敗した。**M8 の C
アプリは最大 2,354 バイトで、どれも 1 フレーム (4KB) に収まっていた**ので、
この経路が一度も通っていなかった。

受け側の `cdk_link_poll` が 1 周で 256 バイトしか汲まない一方、
921600 baud では約 92 バイト/ms 届く。メインループ 1 周（5ms 強）で
500 バイト以上来るので追いつかず、2KB の受信リングが溢れていた。

- 1 周で溜まっているぶんを汲み切る（最初だけ待ち、あとは待たずに繰り返す。
  上限を置いてメインループを止めない）
- 受信リングを 2KB → 8KB

**M8 で入れた「長さと全体の CRC を END で突き合わせる」がそのまま効いた。**
無ければ壊れた `.wasm` が SD に置かれ、「読めません」から転送を疑うまでに
遠回りしていた。

| 見たこと | 証拠 |
|---|---|
| `rs_hello` が C 版と同じ出力 | `m8rs_hello.png` |

#### やっていないこと

- crates.io への公開（パス依存のまま）
- `std` 対応
- C の SDK を置き換えること。**両方を対等に保つ**
- 非同期 / スレッド（ランタイムが 1 本しか走らせない）
- UART は C 版と同じく**実際のデバイスで未検証**（I2C は検証済み。§15.15）

### 15.15 やっていないこと

- WASI 互換 / POSIX 互換
- バックグラウンド実行・ジョブ制御・複数アプリの同時実行
- AOT / JIT（wasm3 はインタプリタのみ）
- ピクセル描画（`gfx_*` は ID 予約のみ）
- ゲスト向けの動的メモリ解放（SDK はバンプ確保のみ）
- 専用フラッシュパーティション（`partitions.csv` は触っていない）
- **UART は実機のデバイスで未検証。** 繋ぐものが手元に無く、ピンの拒否と
  `uart_open` までしか確かめていない。
  （I2C は M5Stack Unit ENV III（SHT30 + QMP6988）を Grove の G17/G18 に
  繋いで検証済み。走査・温湿度の読み出し・走査後にもう一度読めることまで
  確かめた。そこで見つけた 2 つのバグは §12 の 16 と 17。）
